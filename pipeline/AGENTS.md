# pipeline

原典から提供用データを作る層。実行手順は [README.md](README.md)、原典調査・取り込み・PDF抽出・dbt構築のハマりどころは `.agents/skills/pipeline/` を参照する。

## Scripts

script はこの package が所有する。実行は `bun run --cwd pipeline <name>`（または `pipeline/` で `bun run <name>`）。root の `pipeline:*` script はここへの forwarder で、入口となるものだけが root に残る。

| group | scripts |
|---|---|
| 固定入力・構築 | `inputs` / `inputs:migrate` / `acquire` / `build` / `fdp` |
| 観測・調査 | `check:fiscal` / `probe:documents` / `coverage:sources` / `survey:fiscal-years` / `survey:structure` / `eval:extraction` |
| 原典対象の管理 | `sources:plan` / `sources:canonical` / `coverage:fiscal` |
| 取り込み・生成 | `extract:*` / `fetch:*` / `pdf:layer` |
| 検査 | `test`（bun）/ `test:python`（unittest） |

`verify/report`（`@fudoki/report`）と `verify/view`（`@fudoki/pipeline-view`）は別 package。検証報告の生成は `bun run --cwd pipeline/verify/report build`（root の `pipeline:report` と同じ）。

## 生成物・観測・取得の規約

- **commit した生成物には生成手段を残す。** 生成物だけ残して作り方を消すと、作り直せず検証もできない出所不明のデータになる。置き場は調査スクリプト置き場ではなく、生成物と consumer の近く。
- **観測は commit しない。** `ingestion/fiscal/observations/` に書き出し、主張に使うときは実測日を添える。
- **ネットワークを叩く script はサンドボックスを外して回し、CI では回さない。** 開発環境の HTTP プロキシが応答を途中で切り `IncompleteRead` が出る（取得元の問題と取り違えない。実測の詳細は `.agents/skills/pipeline/references/budget-extraction.md`）。

## 技術スタック

- **取得**: Python。原典 CSV/PDF のバイト列と取り込み Parquet を非公開 R2 に保存する。入力一覧 `sources.lock.json`（schemaVersion 3）で原典・表のハッシュとsource宣言をGit管理する。独立したprovenanceは出力しない。
- **OCR**: 共通実装は `ingestion/lib/ocr.py` の llama.cpp + GLM-OCR を使い、重みは `ocr-model.toml` の URL・SHA-256 で固定する。Apple Vision など別エンジンを選ぶ場合は、共通実装を使わない理由・比較評価の有無・エンジンの版と設定を原典別の宣言・コードに記録する。比較未実施なら精度の優位性を主張しない。文字層の抽出・文字対応表の復元を先に検討し、OCR は必要な頁・領域に限定してメモリ使用量を見ながら実行する。詳細は `.agents/skills/pipeline/references/budget-extraction.md` を参照する。
- **変換・検査**: dbt-duckdb。staging は原典の行と1対1、intermediate は構造・単位・科目・分類の統一、marts は提供する列と粒度を確定する。
- **検証**: Bun/TypeScript の `verify/report/` とループバック専用の view。系統・検査結果・原典との対応を確認する。
- **保存**: Git はコード・宣言・判断・入力一覧、非公開 R2 は原典・取り込み表。`.cache/` と `.build/` は再生成可能なローカル作業領域。

  | 内容 | 保存先 | Git |
  |---|---|---|
  | 原典 CSV/PDF、取り込み Parquet | 非公開 R2、個別の内容ハッシュ | 入力一覧だけ |
  | 原典・表の識別子、ハッシュ・保存先、source宣言 | `ingestion/fiscal/sources.lock.json`（schemaVersion 3） | 管理する |
  | 取得元・階層・金額段階の宣言、分類・名称の判断 | `ingestion/` と dbt seeds | 管理する |
  | 復元済み入力・PDF/OCR キャッシュ | `pipeline/.cache/` | 管理しない |
  | DuckDB・dbt manifest・検査結果・ローカル報告 | `pipeline/.build/` | 管理しない |

  再構築に必要な原典・取り込み表・コード・宣言を保持する。独立したprovenanceファイルは生成・保存しない。原典・取り込み表の遠隔保管と復元は確認済みで、repo 内の `data/` は廃止した。
- **一時検証の保存**: `.agent/` へ runtime・依存物・原典群・キャッシュ・全量 warehouse を検証ごとに複製しない。ハッシュ固定した既存原典を読み取り参照し、変更コードのスナップショット・ハッシュ一覧・対象範囲の再抽出と検査結果を保存する。全件走査・全ファイルのハッシュ計算は対象を絞る。採用後の再生成可能な一時DB・重複CSVは整理するが、未採用の原典・取り込み表・支持コード・証跡は保持する。

**Python の版は 3.13 に固定してある。** dbt-duckdb 1.11.0 が classifiers で 3.14 を宣言していないため（`requires-python` は `>=3.10` なので入りはするが、テストされていない組み合わせになる）。

`build` は固定入力から dbt・marts の CSV を生成し、同じ構築 ID の再実行では CSV のハッシュを照合する。

**系統（lineage）は dbt の `manifest.json` から取る。** 手で書かない。
段とノードを手作りすると、パイプラインを変えても図が変わらない状態を作る（実際に作った）。

## パイプラインの層

原典を捨てない **ELT**。変換のルールが変わっても再取得しない。取得・取り込みと配布を dbt の外に置き、dbt のモデルは staging → intermediate → marts に分ける。以下は予算の実装であり、調達にもこの責務の分け方を使う。

| 段 | 実体 | 責務 | やらないこと |
|---|---|---|---|
| **ingestion** | Python | 取得元（CKAN / 自治体の公開資料 / 官公需 API）から取り、原典のバイト列を保存してから、値と単位を変えず Parquet へ取り込む。取得 URL・HTTP status・SHA-256・取得時刻を添える | 解釈・整形・結合 |
| **staging** | dbt | 原典と**1対1**。列名の付け替えと型付けだけ | **判断**（分類、名寄せ、推定）。行を増減させること |
| **intermediate** | dbt | 提供用データのための中間処理。金額の円換算、団体間の構造統一、共通科目への対応、COFOG 分類、会計間移転の判定 | 取得・配布パッケージの生成 |
| **marts** | dbt | 利用者が使う列・粒度を確定する。団体別・全年度の CSV を書き出し、原典由来の金額と判断は列の説明で区別し、COFOG は歳出明細に含める | 新たな分類規則の適用 |
| **説明ファイルの生成** | Python/TypeScript（`fdp/`） | marts の CSV に列の定義・出典・利用条件・証跡を添えて配布物を作る。**親への参照を保持**（①=款・項・目・節） | 金額・分類の再計算 |

**dbt の層は「原典別の準備 → 中間処理 → 利用者向けモデル」で分ける。** 判断の有無は層名とは別に記録する。
風土記の staging は判断を含まないので、**原典と突き合わせて検証できる**。
intermediate で付与した分類などは原典由来の金額と列の説明で区別する。marts は staging を直接参照する場合と、intermediate を経る場合があり、すべてのデータがすべての層を通るわけではない。

⚠️ **境界はディレクトリ名では守れない。テストで縛る。**
原典との**多重集合一致**が「staging に判断が入っていない」ことの検査になる。
これが落ちたら staging に判断が混ざった合図である。
以前 Load を「中間表現へ」と宣言しながら正規化まで実装していたのは、宣言が守られているかを誰も検査していなかったからで、層を増やしても検査が無ければ同じことが起きる。

以前の core を intermediate、package モデルを marts に移した。モデルの参照名（`core_*` / `pkg_*`）と配布データの形式は維持する。命名の整合性だけのために SQL の参照や報告の問い合わせまで変更することは避ける。決定は [ADR 0009](../docs/adr/0009-dbt-model-layers.md)。

**ingestion は冪等**にする（同じ入力なら同じ出力、既存があればスキップ）。
⚠️ **取得元は自治体のサーバである。** 同じ資料を何度も取りに行かない。
取得時の HTTP キャッシュは `.cache/` に置き、通常は24時間再利用する。変更検知の取得はキャッシュを使わず原典を取り直し、実際のハッシュを比較する。
PDF の抽出は1本あたり数十秒かかるので、**抽出を走らせる前に**原典の SHA-256 と
抽出器の版で冪等判定する。冪等でないと `fetched_at` だけが動いて作業ツリーが毎回汚れ、
「再生成しても同じか」を見る CI の判定が意味を失う。**staging 以降は原典だけから何度でも再生成できる**こと。この2つが崩れると、表記ルールを直すたびに全自治体を再クロールすることになる。

## パーサ設計の原則

自治体の公開資料を横断して構造化するときの原則。識別子や階層の扱いは配布物の利用者にも影響するため、取得・抽出の実装と同時に検査を用意する。

**1. id は出現順の連番にしない。中身由来の安定キーにする。**
連番はパーサ修正による行の増減で変わる。予算明細の識別子は、団体・年度・会計・科目階層など、同じ明細を指す情報から導出する。

**2. 構造を潰さない。**
予算資料を事業の一覧だけにすると「どの款・項の下か」が消え、後段の分類に必要な情報が失われる。取り込みでは原典の階層を保つ。

**3. 資料名ではなく中身の粒度で判定する。**
名前が有望な資料が使い物にならないことがある（「予算概要」「予算要求状況一覧表」はどちらも款項レベルの集計で、事業名が1つも載らない）。実際の列構成や PDF の本文を見て、届いている階層と名称の有無を判定する。

**4. 母集団の誤りは後段の精度改善では救えない。**
「一部だけを収録した資料」を母集団にすると、パーサをいくら直しても recall は原理的に出ない。分類の問題ではなくソース選択の問題だから。風土記が目指す範囲は東京都62区市町村だが、収録済みの範囲とは区別する。収録した団体・年度・階層は配布物と報告で示す。

**代表1件は母集団ではない。** manifest の `openData.budget` のような「団体ごとの代表」を全体だと思って測ると、結論が反転する。実際に `check:fiscal` の初版はこれで「事業単位のデータは0件」と誤判定した（代表1件がたまたま指標表だっただけで、同じ団体が28件のデータセットを持っていた）。**「無い」と言う前に、探し方が母集団を張れているか**を疑う。

**検索クエリも母集団ではない。** その次の版は全文検索のクエリ語で候補を集めており、
予算資料を持つ17団体のうち8団体しか見えていなかった。**しかも形式で CSV に絞っていた**ので、
XLSX / XLS でしか出していない9団体が「予算データ無し」に見えた（2026-08-30 実測）。
どちらも「見つかったものの中で正しく判定する」問題ではなく、**見に行っていない**問題である。
いまは団体ごとに全データセットを列挙する。**取りこぼしの3つの入口は、
母集団・形式・語彙**（事業階層の推定語に「細目」が無く、多摩市を1年近く落としていた）。

**5. 例外は一般化せず、その対象に閉じる。**
レイアウトの差を全対象共通のルールにすると、他の原典の抽出を壊すことがある。団体・年度・資料ごとの違いは取得元の宣言とレイアウト定義に閉じ、共通処理を変更したときは対象の原典で抽出結果を比較する。

**6. 分類できない行を捨てない。**
共通科目や COFOG に割り当てられない行も、原典由来の金額として残す。分類できなかった状態を別に示し、未分類の金額が集計から黙って消えないようにする。

**7. 一次レスポンスは全部保存する。**
後から欲しくなった項目を取り直すより、最初に丸ごと持つ方が安い。raw + provenance で既に採っている型（原文 + 取得URL + HTTP status + SHA-256 + 取得時刻）を Extract 全体に適用する。

### 測れる状態を先に作る

識別子と抽出規則を変更するときは、次の検査で影響を確認する。

- **識別子の対応**: 変更前後で同じ予算明細を同じ識別子で参照できるか。
- **抽出結果の検査**: 原典の小計・合計との一致を確かめ、抽出器を変更したときは団体・年度ごとの結果を比較する。
