# 形式別に取り込み表を検査する

## CSVの検査は変換に組み込む

選定済みのヘッダー付きCSVを、原典列は文字列のままParquetへ変換する。共通実装は [conversion.py](../../../../pipeline/ingestion/lib/conversion.py) の `convert_csv()` と `verify_csv()`、管理側の入口は [csv/convert.py](../../../../pipeline/ingestion/fiscal/layouts/csv/convert.py) である。

1. 上流が指定した文字コード・区切り文字・引用符を使用する。原典のSHAを変換前後に照合する。
2. ヘッダー、列数、引用符、文字コードのデコードを厳密に処理する。欠けた列や不正な文字を飛ばして継続しない。
3. Parquetを書いた後、原典CSVを先頭から読み直す。原典列の名前・順序・VARCHAR型、データ行の全セル・行順・重複・空文字を照合する。追加の物理行範囲列も照合する。
4. 不一致では停止する。共通変換は検査で拒否した新規Parquetを除去し、管理側はR2保存・管理JSON更新へ進まない。
5. 管理側のCSV変換は候補dirへ `<表ID>.checks.json` を出す。CLI全体の成功と、成否、原典SHA、変換設定、成功時の表SHA・行数を確認する。個別表の検査が通っても、原典の途中変更や別表の失敗でCLIが停止した候補は取り込み完了にしない。失敗位置は行／列で報告し、全セルをcontextへ出さない。

行数や合計だけを比べない。重複行の置換、空文字のNULL化、先頭ゼロ・空白・引用された改行の消失は、行数や合計が同じでも誤変換である。

CSVの合計が原典内で一致すること、原典の財政上の正しさ、金額の数値化は取り込みの合否条件にしない。原典に不整合があっても、その値を保持する。指定した文字コードが意味上正しいかは上流・書式設定で確認する。デコード成功と全セル一致だけで、誤った文字コード指定を必ず検出できるわけではない。

ヘッダーのみのCSVは変換関数では0行として保持できるが、管理入口では未確認の0行を拒否する。ヘッダーなし・前置き付きの専用変換と、旧Parquetを移す `retained` は、この共通CSV検査に合格済みと扱わない。

## PDFの既存検査を転用する

PDFの共通検査フローと合否条件は未確定である。従来の候補検査から、次の観点を使う。

- 金額セルを科目番号・積算根拠と区別し、年度・会計・単位・金額段階を原典の見出しと照合する。当年・前年の金額列を混ぜない。
- 目・事業・節の独立した印字小計や合計と照合する。目的別と性質別、事業別と節別の分解を足し合わせない。説明欄の下位内訳が任意の場合は完全な内訳と仮定しない。
- 名称・階層・原典位置・未読セル・欠落・二重収録を確認する。合計一致だけでは、同額の行の取り違えや名称の欠損を検出できない。
- 補正は符号付き基準額・増減額・補正後額を区別する。未収録の変更をゼロにせず、承認や事業×節の対応が未確認なら確定値へ変えない。
- 転記・訂正宣言と凍結したOCR観測は、その対象範囲を確認する。`reconciled` は印字合計との一致、`amount_status` は読み取り状態、page/bboxは位置を示す。全頁を目視確認済みという意味にはしない。

書式別の検査コードは各団体の `layouts/`、共通の見開き検算は `fiscal/layouts/fiscal_general/extract_statement.py` にある。新しい `statement/convert.py` は検算結果を出すが、不一致を保存前に拒否する共通条件には未接続である。CSVと同じ保証があると扱わない。

## 後段の検査へ転用するもの

登録とSQLの検査は、取り込みの内容保持と分けて [dbt](dbt.md) で行う。

- `all_sources()` と原典宣言の実行結果で対象dataset・方向・文書種類・金額段階を確認する。定義があっても返り値に入らなければ登録済みと扱わない。
- raw → staging → intermediate → marts → CSVを実行し、値と単位、原典行の対応、欠落・二重収録、集約を確認する。stagingの行数一致だけで全値一致としない。
- 単位・段階の根拠は原典から取る。宣言どうしの一致だけでは、両方が同じ誤りを含む場合に検出できない。
- 全列・型・NULL・重複数の比較を必要なモデルに適用する。提供用モデルの単位換算・集約には宣言した変換を考慮し、全raw列がそのまま残ることを要求しない。

資料別の監査やscopedなSQLの成功は、検査した範囲として報告する。全体への影響は全量build、収録範囲の完了は通常監査で確認する。
