# 形式別に取り込み表を検査する

## CSVの検査は変換に組み込む

選定済みのヘッダー付きCSVを、原典列は文字列のままParquetへ変換する。共通実装は [conversion.py](../../../../pipeline/ingestion/lib/conversion.py) の `convert_csv()` と `verify_csv()`、管理側の入口は [csv/convert.py](../../../../pipeline/ingestion/fiscal/layouts/csv/convert.py) である。

1. 上流が指定した文字コード・区切り文字・引用符を使用する。原典のSHAを変換前後に照合する。
2. ヘッダー、列数、引用符、文字コードのデコードを厳密に処理する。欠けた列や不正な文字を飛ばして継続しない。
3. Parquetを書いた後、原典CSVを先頭から読み直す。原典列の名前・順序・VARCHAR型、データ行の全セル・行順・重複・空文字を照合する。追加の物理行範囲列も照合する。
4. 不一致では停止する。共通変換は検査で拒否した新規Parquetを除去し、管理側はR2保存・管理JSON更新へ進まない。
5. 管理側のCSV変換は候補dirへ `<表ID>.checks.json` を出す。CLI全体の成功と、成否、原典SHA、変換設定、成功時の表SHA・行数を確認する。個別表の検査が通っても、原典の途中変更や別表の失敗でCLIが停止した候補は取り込み完了にしない。失敗位置は行／列で報告し、全セルをcontextへ出さない。

行数や合計だけを比べない。重複行の置換、空文字のNULL化、先頭ゼロ・空白・引用された改行の消失は、行数や合計が同じでも誤変換である。

CSVの合計が原典内で一致すること、原典の財政上の正しさ、金額の数値化は取り込みの合否条件にしない。原典に不整合があっても、その値を保持する。指定した文字コードが意味上正しいかは上流・書式設定で確認する。デコード成功と全セル一致だけで、誤った文字コード指定を必ず検出できるわけではない。

ヘッダーのみのCSVは変換関数では0行として保持できるが、管理入口では未確認の0行を拒否する。ヘッダーなし・前置き付きの専用変換と、旧Parquetを移す `retained` は、この共通CSV検査に合格済みと扱わない。

## PDFの金額検査と修正ループ

PDFの金額検査は、階層ごとに「直下の内訳の合計＝原典に印字された親の金額」を照合する。以下は合意した目標手順であり、全書式への共通実装・自動停止条件が完成済みという意味ではない。新たな検査機構を先に増やさず、集計・差分の一覧と修正・再検査を基本にする。CSVの取り込み完了条件は上の全セル保持検査のままとする。

### 構築と検査を分担する

- **構築担当はsubagent。** 親agentが指定した原典・対象範囲・出力形式に従い、抽出コードと書式設定を作成・修正し、新しい候補Parquetを生成する。原典SHA、処理範囲、出力先、再実行方法、変更内容と未確認事項を返す。自分で動作確認しても、最終的な合否判定や検査基準の変更は担当しない。
- **検査担当は親agent。** 保存されたParquetと原典を自分で読み、文字保持・所属・階層ごとの合計を検査する。不一致の一覧、原因の見立て、次の修正依頼、再検査と完了判断を担当する。subagentの「成功」という報告や、構築コードの再計算との一致だけで合格にしない。
- 検査担当は、原典・対象範囲・出力形式と変更してよいコードの範囲を構築担当へ渡す。修正依頼は不一致の対象と原典の根拠を示し、合計に合わせる訂正値を推定して渡さない。修正のたびに同じ構築担当へ返し、生成物の更新と合否判定の責任を混ぜない。

### 階層ごとの合計を比較する

| 集計する内訳 | 比較する原典の金額 |
| --- | --- |
| 説明欄の末端明細を、確認済みの所属に従って目・節ごとに集計 | 同じ目の法定節一覧の節額 |
| 同じ目に属する節額 | 目の金額 |
| 同じ項に属する目の金額 | 項の金額 |
| 同じ款に属する項の金額 | 款の金額 |

- 保存した明細Parquetを読み戻して集計する。法定節一覧だけを足して目と比較しても、説明欄から作った明細の欠落は確認できない。説明に事業階層がある場合も、確認済みの節への所属に従って当該目内の事業をまたいで集計する。原典で節への対応が確認できない場合は、節を推定で付与しない。
- 比較は同じ原典対象・会計・年度・金額段階・金額列・単位・収録範囲の中で行う。名称だけで別の項や目をまとめず、原典のコード・所属経路で区別する。検査用に数値化し、rawの原文・単位は変えない。
- 明細に反復した親の金額は、原典上の親項目ごとに一度だけ数える。同じ親の反復値が一致することを確認し、不一致なら先頭の値を選んで続けず一覧へ出す。金額だけの重複除去（`SUM(DISTINCT 金額)`など）は、同額の別項目を失うため使わない。小計とその内訳を同時に足さない。
- 完全な内訳と印字合計が揃った比較だけを「一致／不一致」とする。継続頁・未収録・未読・所属未確認は「保留」、原典に比較する合計や完全な内訳がない場合は「検算不可」とし、理由を示す。欠けた金額を0で補わず、部分範囲の成功を全体の成功にしない。
- 文字保持・原典との対応の検査は残す。合計一致だけでは名称の欠損や同額の取り違えを検出できない。法定節一覧と説明欄、財源内訳など独立した分解を足し合わせない。

### 不一致をまとめ、修正して再検査する

1. 構築担当が指定範囲を構築する。検査担当は読み戻したParquetで実行可能な階層の比較を一通り行う。最初の不一致だけを直し始めず、まず対象範囲の結果をまとめる。
2. 検査担当が既存の検査レポートに、不一致・保留・検算不可を一覧化する。各項目に比較した階層と所属経路、原典の頁・位置、印字合計、内訳合計、差額、対象範囲と理由を示す。未確認の値・原因は推測で埋めない。ユーザーには件数・対象・レポート参照を短く返す。
3. 検査担当が一覧を原典と照合し、欠落・二重収録・誤読・誤所属・範囲不足・原典自体の不整合を切り分け、次の対応をまとめて構築担当へ返す。下位の誤りによる上位の不一致は関連付け、同じ原因を別々に直さない。既存構造の変更が必要なら、その必要性と影響を説明してユーザーの判断を受ける。
4. 構築担当が確認した原因に応じて、抽出コード・書式設定・対象範囲を修正する。必要な領域だけ再読し、新しい候補Parquetを構築する。合計を合わせるための推定・配賦や、Parquetへの直接書き換えはしない。個別訂正の扱いは [取り込み時の修正手順](ingestion.md#誤りが見つかったときの修正) に従う。
5. 検査担当が影響する明細とその上位階層を再検査し、文字保持・保存後の読み戻しも確認する。同じ書式へ適用する修正なら、その影響範囲も確認する。一覧を更新して、解消・残存・新規の問題と次の対応を示す。繰り返し不一致になる場合は、下の前提の見直しへ進む。
6. 検査担当が、対象範囲の不一致が解消し、保留が解決した範囲を完了とする。検算不可・原典の不整合など解消できない事項は理由と次に必要な確認を残し、検査済みの範囲と区別して報告する。根拠のない修正や同じ条件での再実行を繰り返さない。

### 不一致が繰り返すときは検査担当が前提を見直す

同じ不一致が修正・再検査を重ねても残る、または差額・件数が改善しない場合は、局所修正を続けず、検査担当が構築方法と検査方法の前提を見直す。目安は同じ問題に対する2回程度の修正後であり、独立した欄の誤結合など前提の誤りが明らかなら初回から見直す。既知の範囲不足による保留を、修正失敗の回数に数えない。

検査担当は原典の該当範囲へ戻り、階層と行の粒度、節・説明・財源の関係、継続頁、単位・金額列、親金額の反復や二重加算を再確認する。構築側だけが間違っていると決めず、検査の集計キー・比較対象・完全な内訳という仮定も確認する。確認した根拠と改める前提をまとめ、構築担当へ修正方針を渡して再構築・再検査する。通過させるために検査基準を緩めたり原典値を書き換えたりしない。構造変更が必要な場合は、既存構造を歪めずユーザーへ判断を返す。

構築・検査・一覧の更新はコードで行い、LLMは不一致の原因確認と修正方針の判断に使う。検査結果や修正待ち状態をrawの列へ追加せず、独立したprovenanceファイルや新たな状態管理基盤を作らない。

## PDFの既存検査を転用する

金額検査は上の階層ごとの合計比較と修正ループを基本とする。書式別の原典照合・共通の実装と停止条件は未完了であり、従来の候補検査から次の観点を転用する。

- 金額セルを科目番号・積算根拠と区別し、年度・会計・単位・金額段階を原典の見出しと照合する。当年・前年の金額列を混ぜない。
- 目・事業・節の独立した印字小計や合計と照合する。目的別と性質別、事業別と節別の分解を足し合わせない。説明欄の下位内訳が任意の場合は完全な内訳と仮定しない。
- 節一覧と説明欄は内部の構築・検査で分離する。説明内の節見出しと同じ目の節一覧への対応が確認済みなら、その所属と事業・節・細目の経路を検査する。未確認なら目への所属だけを保持する。同じ高さの行や名前だけで節との関係を生成していないか、出力内の所属と原典階層経路を検査する。別表の結合や親IDからの経路構築をdbtへ残さない。説明欄の末端を基準とする明細では名称・金額・階層が通常の列へ展開され、JSON・配列・STRUCT列や法定節一覧の検算用の区分・金額が混入していないことを確かめる。説明内の階層が節であるという確認済みの解釈もmetadataと照合する。原典に配分額がない財源を説明の細目へ割り当てない。誤結合による金額不一致は調査の手掛かりになるが、総額の一致だけでは誤った対応を除けない。同額の行の取り違えや、値を変えず関係だけ変えた候補も拒否できる検査にする。対象範囲の最後に見えた項目を、継続中の状態から確認済みの末端へ変えた候補も拒否する。
- 名称・階層・原典位置・未読セル・欠落・二重収録を確認する。合計一致だけでは、同額の行の取り違えや名称の欠損を検出できない。
- 補正は符号付き基準額・増減額・補正後額を区別する。未収録の変更をゼロにせず、承認や事業×節の対応が未確認なら確定値へ変えない。
- 転記・訂正宣言と凍結したOCR観測は、その対象範囲を確認する。`reconciled` は印字合計との一致、`amount_status` は読み取り状態、page/bboxは位置を示す。全頁を目視確認済みという意味にはしない。

書式別の検査コードは各団体の `layouts/`、共通の見開き検算は `fiscal/layouts/fiscal_general/extract_statement.py` にある。新しい `statement/convert.py` は検算結果を出すが、不一致を保存前に拒否する共通条件には未接続である。CSVと同じ保証があると扱わない。

## 後段の検査へ転用するもの

登録とSQLの検査は、取り込みの内容保持と分けて [dbt](dbt.md) で行う。

- `all_sources()` と原典宣言の実行結果で対象dataset・方向・文書種類・金額段階を確認する。定義があっても返り値に入らなければ登録済みと扱わない。
- raw → staging → intermediate → marts → CSVを実行し、値と単位、原典行の対応、欠落・二重収録、集約を確認する。stagingの行数一致だけで全値一致としない。
- 単位・段階の根拠は原典から取る。宣言どうしの一致だけでは、両方が同じ誤りを含む場合に検出できない。
- 全列・型・NULL・重複数の比較を必要なモデルに適用する。提供用モデルの単位換算・集約には宣言した変換を考慮し、全raw列がそのまま残ることを要求しない。

資料別の監査やscopedなSQLの成功は、検査した範囲として報告する。全体への影響は全量build、収録範囲の完了は通常監査で確認する。
