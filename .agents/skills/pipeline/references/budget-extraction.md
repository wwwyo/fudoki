# B. 取り込み・抽出候補と本体への追加案を作る

## 入力と作業

- Aで確認した原典・年度・会計・版・頁境界と、未確認事項を受け取る。別年度の組版を確認なしに使い回さない。
- CSVは文字コード・列構成を確かめ、原典の値と単位を保つ取り込み表を作る。PDFは文字層・文字対応表の復元を先に検討し、必要な場合にOCRを使う。
- OCRの共通経路は `pipeline/ingestion/lib/ocr.py` のllama.cpp＋GLM-OCRである。別エンジンの選択理由・比較評価は調査記録、版・設定はコードと抽出宣言で管理する。比較未実施を優位性の根拠にしない。
- 団体・年度・会計・方向ごとの頁と組版を宣言し、原典の行・頁・位置・印字値から候補を作る。意味が未確認の観測を、確定した金額段階や事業×法定節へ繰り上げない。
- 取り込み表だけでなく、原典から再抽出する処理、必要な宣言、dataset登録、staging・intermediate・marts・CSV・監査への接続案を揃える。既存入力・登録を保持する。

## 保存するもの

- 候補は `.agent/` や `pipeline/.cache/` の作業別出力先へ置く。既存の採用入力を候補生成の都合で上書きしない。
- `provenance.json` とconstruction-provenanceは生成しない。候補はParquetと `inputs.lock.json`（原典・表のハッシュと保存先、source宣言）を出す。抽出の要約・検査結果は実行出力または再生成する検証レポートへ出し、source宣言へ成功判定や検査結果の複製を入れない。
- 現行の通常PDF抽出は `extract_statement.py` の `--sources`・`--raw-root` で宣言と候補出力先を指定できる。専用処理はそのCLIと宣言を読む。
- `sources.lock.json` への採用はFで行う。候補の入力一覧があることを採用済みとは扱わない。

## 取り込み表の保存形式（合意した方針）

- Bの候補表と、固定入力として採用する取り込み表はParquetに統一する。明示した列型・NULL・原典の文字列を保ち、表から直接Parquetを生成する。CSVを中継して型を推論し直さない。
- Bの抽出結果はCSVを併出しない。閲覧のためにもCSVを常時生成・保存せず、Parquetを直接読む。候補と同じ表を別形式で重複保存しない。
- 自治体が公開した原典CSVは原典のバイト列としてそのまま保存する。この方針は原典の改変を意味しない。
- Gitで編集する小さな対応表・分類規則等のdbt seedと、提供用martsのCSVは別の役割を持つ。Bの取り込み表の統一を理由に、それらの形式を変えない。現行dbtの取り込み入力は `models/staging/fiscal/_sources.yml` の `read_parquet` で直接読む。
- これは保存形式の方針であり、全専用処理の移行が完了したという記録ではない。以下の「実際に出る候補ファイル」にはCSVとParquetを併出する既存実装も含む。変更時は読み戻した列型・値・NULL・行数を確認する。

## Cへ渡す条件と限界

- 候補表、原典への参照、候補の入力一覧・検査結果、抽出・登録・SQLの追加案と実際の検査結果を渡す。
- 抽出器が行う内部検算も結果として残す。ただし候補の出力成功だけでは、Cの原典の意味・各層の照合やDの再抽出が通ったとは言えない。
- 原典に節がない目、独立した内訳、判定できない金額・年度・単位は欠落やゼロへ置き換えず、確認できた粒度と未確認事項を残す。
- 提出形式・提出前検査を統一する共通コマンドは未確立である。候補と本体への追加一覧を実ファイルで確認する。

## 誤読が判明したときの現在の修正方法

- 列境界・頁範囲・文字対応表・行のまとめ方が原因なら、抽出宣言またはコードを修正し、候補を再抽出する。通常PDFの `extract_statement.py` は候補を再抽出して内部検算を実行する。補助抽出器のキャッシュは候補の入力一覧にある原典・抽出器の版で判断する。
- OCRの特定セルは、原典画像を確認した個別訂正を使う経路もある。千代田区2025年度は `chiyoda2025_native/correction-ledger.json` に訂正値・除外理由を記録し、`replay.py` の `DIRECT`・`PHANTOM`・セル対応処理等で適用する。ledgerを読む共通訂正器ではなく、この資料の専用処理である。
- 個別訂正は原典SHA・頁・観測ID・位置で対象を限定する。元の `raw_text` を保持し、`observed_amount`、`amount_status`、`related_fields_json` 等へ訂正値と根拠を別に保存する。例としてp154の一観測は `raw_text='124'` を残し、同じ印字セルの確認済み値424と対応づけている。
- 印字がない観測や判定できない文字は、同じ合計になる数字へ補正しない。千代田区の専用処理では元の観測を保持して数値をNULLとし、未解決セルの表へ残す。
- 修正後は候補を再生成し、内部検算をやり直す。C・Dの検査を通す範囲は別に確認する。全経路に共通の訂正形式・自動修正手順は未確立である。

## 実際に出る候補ファイル

- 通常のCSV取り込み・PDF抽出は、入力経路別の `data.parquet` と候補の `inputs.lock.json` を生成する。通常PDFの行には科目・事業・内訳・金額、原典頁・bbox、表ID・単位・年度、目合計との突合結果等が入る。対象により列は異なる。
- 観測を分ける専用処理は、頁、元の文字・位置・候補、欄別観測、金額セル、目の統制値、独立した節・説明欄、未解決セルを別表にする。千代田区2025年度の `replay.py` は8種類のCSVを生成し、`--parquets` では対応する8表を `locked-tables/` に生成する。
- 同じ専用処理は非加算の参照CSV、`materialization-manifest.json`（出力ごとの役割・行数・型・SHA・サイズ）も生成する。候補内のファイル名が `staging`・`intermediate`・`marts` でも、通常dbtへ統合した証拠とは扱わない。
- 本体への追加案には抽出・登録コード、宣言、SQL、監査処理、追加一覧もある。これらはデータ本体とは分けてCへ渡す。

## 既存の取得・抽出で実測した注意点

- **⚠️ HTTP を分割して読むと切り捨てが成功扱いになる。** 実際に 2.3MB のうち約 30KB を失っていた。
  引数なしの `read()` と Content-Length 突合で検知する

- **⚠️ 文字がアウトライン化された PDF がある。** テキスト命令を持たず全グリフが曲線として
  描かれており、テキスト抽出が原理的に成立しない。OCR（`ingestion/lib/ocr.py`）で読むが、
  **誤読が混ざる前提の経路**として扱う — 金額を原典と突合し、一致した範囲だけを使う。
  ページ全体を一度に OCR しない（列をまたぐ語の融合で座標が壊れる。列ごとに切り出す）

- **⚠️ 法定様式でも、1つの論理行が2頁にまたがることがある**（見開き）。
  頁ごとに行へまとめてから突き合わせてはいけない — 片方で名称が折り返し片方は1行、
  という行数の食い違いが普通に起きるので、行番号では対応が取れない。
  2頁の文字を1つの座標系へ合わせてから行にまとめる

- **⚠️ 同じ資料でも列の x が direction で割れる。** 歳入の目の欄は名称が折り返さない幅、
  歳出は数文字で折り返す幅、ということが実在した。片方の実測を両方へ当てると、
  一方では名称が金額の欄へ、他方では金額が欄外へこぼれる

- **⚠️ 表の欄を固定の境界で割らない。両方向にこぼれる。** 長い名前が金額側へ
  こぼれる行（1団体目）と、桁の多い金額が名前側へこぼれる行（2団体目、**30 目**が
  突合に落ちた）が両方とも実在した。境界で割ると**その行だけが丸ごと落ちる**。
  どの欄も名前が左寄せ・金額が右揃えなので、行末から数字の連なりを切り出せばよく、
  割り方は表の中に1つで足りる。同じ理由で、入れ子の段は**名前の左端ではなく金額の右端**で
  決まる（長い名前は下の段の字下げ位置を越えて右へ伸びる）

- **⚠️ 項目に通し番号を振る団体がある**（`１ 議員報酬（区議会事務局）`）。番号は目の中の
  並び順しか表していないので落とす（並びは `source_row` が保つ）。残すと年度をまたいで
  番号がずれ、同じ事業が別の名前に見える。**⚠️ 自動判定にしない** —
  番号を振らない団体では `1歳6か月児健診` のような正しい名前を削ってしまう

- **⚠️ 金額に単位が付く団体がある**（`316,980 千円`）。行末が数字で終わらないので、
  単位を落としてから切り出す。**落とせない行を弾く働きも兼ねる** —
  積算根拠の `21,400人` `98.0％` はそこで自然に除かれる

- **⚠️ 見出しは継続の頁で再掲される。** 見出しを見るたびに文脈を畳むと、
  継続した明細が行き場を失って黙って落ちる。畳むのは**値が実際に変わったとき**だけにする

- **⚠️ 名前は金額と別に折り返す。しかも「次の行」が続きとは限らない。**
  説明欄には、金額だけが次行へ回る行・名前が次行へ続く行・目ごとのリード文・積算根拠が
  同居する。持ち越した名前を無条件に捨てると**項目名が途中で切れたまま配布物に出る**し、
  無条件に繋ぐとリード文や積算根拠が名前に混ざる。**行頭の字下げが揃う行だけを続きとみなす**
  （折返しは行頭が揃い、リード文と積算根拠は字下げが違う）

- **⚠️ 折り返した名称が確定するのは、その行より後である。** 名称を値でその場に写すと、
  **その科目の最初の1行だけが折返し前の名前を持つ**。金額は動かないので合計突合では出ない。
  名札を参照で持たせて、抽出が終わってから畳む

- **⚠️ 内訳を持たない科目がある**（予備費）。葉だけを行にする設計だと、
  その科目の額が配布物から丸ごと消える。科目そのものを葉として残す

- **⚠️ `IncompleteRead` は取得元の性質ではなく開発環境の問題だった。**
  原因は開発環境が通す HTTP プロキシ（切れる位置が毎回一致することから切り分け）。
  **再試行は入れない** — 本物の切断を握りつぶして失敗を遅らせるだけになり、
  「切り捨てを成功として扱わない」という取り込みの柱と逆を向く
