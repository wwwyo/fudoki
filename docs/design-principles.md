# 設計方針・対象・パイプライン・パーサ原則

構造・標準・配布・分類の判断を変えるときの正本。
決定の記録は `docs/adr/`。

## 設計方針

**1. 独自スキーマを発明しない。ただし1本の標準に全部を載せようとしない。**
標準に載ること自体が相互運用性の主張であり、自作すると必ず既存ツールから外れる。ただし守備範囲は3つに割れているので、**3本の標準を使い分け、継ぎ目も標準が規定した場所で繋ぐ**。

| レイヤ | 標準 | カバーするもの |
|---|---|---|
| **① 何にいくら** | [Fiscal Data Package 1.0.0](https://fiscal.datapackage.org/) | 列を **fiscal concepts（ColumnTypes）** で意味づける（コロン区切りの階層。例 `administrative-classification:generic:code`）。全要素が任意。予算は **Budget Standard Taxonomy**、支出実績は **Spending Standard Taxonomy**。**Budget 側に COFOG（`functional-classification:cofog:division:code` 等）と GFSM の列型が定義済み**で、分類表を自作しなくてよい |
| **② いつ何が公告されたか** | [OCDS](https://standard.open-contracting.org/latest/en/schema/reference/) | 調達プロセス全体（planning → tender → award → contract → implementation）。Apache 2.0 / JSON Schema。**ただし官公需 API が埋めるのは tender まで**（後述） |
| **③ どう決まったか** | [Popolo](https://www.popoloproject.com/) | Person / Organization / Post / Membership / **Motion / VoteEvent / Vote** / Speech。本文構造は [Akoma Ntoso](https://www.oasis-open.org/standard/akn-v1-0/) 互換を意識する（完全準拠は後追いでよい） |

継ぎ目:

- **① ↔ ②** — OCDS の `planning.budget` が `id` / `amount` / `projectID` に加えて **`uri`＝機械可読な予算データへのリンク**を持ち、仕様が FDP との連携を明記している
- **① ↔ ③** — Popolo の `Motion`（議案）と `VoteEvent` / `Vote`（議決）。**会議録を Speech の山として扱わない** — 予算案という議案とその議決まで語彙がある
- **事業者の同一性** — OCDS の `parties`。ただし**官公需 API に事業者は載っていない**（下記）ので、この継ぎ目は現状つながっていない

**Popolo は財政の語彙を持たない。** 予算側を Popolo に載せようとすると必ず独自拡張になるので、そこは FDP を使う。

⚠️ **参照先を間違えないこと。** FDP の現行は `fiscal.datapackage.org` の **1.0.0**。
前身（0.3.0）や旧サイト（1.0-rc.1）を現行と誤読しない。`profile: "tabular-data-package"` は
正しい値で、**「これは FDP である」を宣言する口は仕様上どこにも無い**ので `fudoki.specification`
を版の宣言として持つ。この事実は配布物に書かない（利用者のすることが変わらない）。

⚠️ **採用した3標準のうち FDP と Popolo は更新が止まっている**ので、
「止まったら自分で維持する」は保険ではなく既定の運用（方針3）。
FDP 採用自体は変えない（予算の事業別明細を対象にする現役の代替が無い）。
実測の根拠は `docs/fdp-spec-notes.md`。

**分類 dimension は 款→項→目→節 と COFOG の2本を張る。** COFOG 写像は後付け機能ではなく一級の要件で、自治体間比較にも将来の国際比較にも同じ写像が効く。後回しにすると両方作り直しになる。

**COFOG も階層である**（division 01 → group 04.5 → class 04.5.1）。
規則は**決まった粒度をそのまま `cofog_code` に持つ**（`01` / `04.5` / `04.5.1`）。
⚠️ **division / group / class を別々に宣言しない** — 同じ事実が3箇所へ分かれ、
粒度を下げたときに片方だけ古くなる。配布物では分解して3列で出すが、宣言は1つである。
⚠️ **粗い粒度は誤りではない。** 款の名称だけで決まる規則（総務費 → 01、民生費 → 10）は
division 止まりが正しく、group を埋めるには項や目まで下げる判断が要る。
**空は「該当が無い」ではなく「まだ降りていない」**を意味する。

**2. 特定自治体向けサイトではなく汎用層として作る。**
mySociety が TheyWorkForYou（UK専用サイト）と SayIt（汎用ツール）を分離したから、南アフリカやフィラデルフィアが再利用できた。同じ分け方をする。「他自治体でも動く」を口約束ではなくコードで示す。

**3. 運営者が消えても止まらない形にする。**
先行事例は3つの死に方をした。**個人運営は消滅**（chiholog は798自治体を横断検索していたが現在 DNS ごと消えている）、**会社運営は無料枠の線引きを握られた**（Open States は Plural に買収後、非商用のみ無料・GraphQL v2 はサンセット）、**標準そのものが止まった**（Fiscal Data Package は 2024-03 を最後に更新なし）。コード・宣言・判断・採用した入力一覧を Git に残し、原典を非公開 R2 に保管する。固定入力を復元して CI で再構築できる形にする（コードは MIT）。

⚠️ **ライセンスは1つに畳めない。** コードは fudoki のものだが、原典と正本は各自治体のもので、
**持っていない著作権にライセンスは与えられない**。root の `LICENSE`（MIT）を data/ まで及ぶと読ませると、
CC BY が求める帰属を下流が落とす。層ごとの宣言は `docs/data-license.md` と各 `datapackage.json` にあり、
原典のライセンスは団体ごとに `pipeline/ingestion/fiscal/sources.toml` が持つ。
判断のリソースを CC BY 4.0 にできるのは原典が継承を求めないからで、CC BY-SA の団体が入れば
その選択は成り立たなくなる（`pipeline/fdp/build.py` が停止する）。
⚠️ **原典が1種類とは限らない。** 事業名を市サイトの決算資料 PDF から起こしている団体があり、
そちらは再配布の可否が未確定である。配るのは抽出した事実で、事実に原典のライセンスは付いてこないが、
`sources` と `fudoki.factsFrom` に**出典としては書く** — 利用者が列の出所を辿れる必要がある。

**入力と判断から、配布用と API 用の表を生成する。** Git はコード・取得元・判断・入力一覧を保持し、R2 は原典・取り込み・証跡・配布物、D1 は検索用の表を保持する。公開 API と独立した download Worker を置き、API が停止しても一括配布を取得できる。入力一覧・内容ハッシュ・release manifest で版を追い、R2 以外へのバックアップも残す。移行と運用の詳細は [全体設計](design-doc-monorepo.md) と [pipeline の手順](../pipeline/README.md)。

**ダッシュボードは `https://fudoki.dev/` で配信する。** これは派生物であって正本ではない。
画面と API が停止しても配布物は独立した download Worker から取得できる。
配布物の絶対 URL（`canonical` / `og:image` / `sitemap.xml`）はこのドメインを指す。
⚠️ **ルートパス（`https://fudoki.dev/`）で配信する前提**なので、`vite.config.ts` の `base` は `/` のままでよい。
`base` に効くのは**パス**であって DNS 名ではない。`www.fudoki.dev` のようなサブドメインへ移しても `/` のまま。
サブパス（`example.github.io/fudoki/` のような形）へ移すときだけ、`base` と上記3箇所を同時に変える
（片方だけだと静的アセットが 404 になる）。
置き場は Cloudflare。apex をそのまま向けられるのは Cloudflare が CNAME flattening をするからで、
`CNAME` ファイルは要らない（GitHub Pages なら要る）。

配信は **Cloudflare Workers の静的アセット**（`apps/web/wrangler.jsonc`）。`main` を持たない
アセットだけの Worker で、画面はサーバ側で何もしないのでスクリプトは置かない。

公開 web は API から dataset と release を選び、SQL 集計の応答を表示する。build/deploy は公開 UI のコードだけを扱い、dbt・報告・原典の全量生成は実行しない。

```bash
bun run deploy:web    # vite build → wrangler deploy
```

ローカル検証画面は `pipeline/verify/view/` にあり、報告は `pipeline/build/report/`、PDF 閲覧レイヤは `pipeline/.cache/pdf/` に置く。公開 web の配信物には含めない。

`apps/web` の運用ハマりどころ（デプロイ後の確認方法・`DESIGN.md` に何を書くか）は
`.agents/skills/web-frontend-ops/`（session-retro が維持）を参照。

`apps/api`（Cloudflare Workers + oRPC）のデプロイ・運用のハマりどころは
`.agents/skills/cloudflare-api-ops/`（session-retro が維持）を参照。

**原典 CSV/PDF と取り込み済み Parquet は別のものとして保管する。** 原典・表・証跡は非公開 R2 の内容ハッシュ別オブジェクト、配布物は release 別の R2。Git の `pipeline/ingestion/fiscal/sources.lock.json` が採用した個別キーとハッシュを固定する。新規の取得は原典を保存してから表を作る。固定入力からの build で原典の再取得をしない。

会議録の原文の公開可否は既存の `gate.redistribute` に従う。非公開の保管と公開する配布物を同一の判断として扱わない。権利の整理は [データの利用条件](data-license.md)、個別条件は取得元の宣言と descriptor に残す。

以前 Load を「中間表現へ」と宣言しながら正規化まで実装していたのは、宣言が守られているかを誰も検査していなかったからで、層を増やしても検査が無ければ同じことが起きる。

以前の core を intermediate、package モデルを marts に移した。モデルの参照名（`core_*` / `pkg_*`）と配布データの形式は維持する。命名の整合性だけのために SQL の参照や報告の問い合わせまで変更することは避ける。決定は [ADR 0009](adr/0009-dbt-model-layers.md)。

**ingestion は冪等**にする（同じ入力なら同じ出力、既存があればスキップ）。
⚠️ **取得元は自治体のサーバである。** 同じ資料を何度も取りに行かない。
取得時の HTTP キャッシュは `pipeline/.cache/` に置き、通常は24時間再利用する。変更検知の取得はキャッシュを使わず原典を取り直し、実際のハッシュを比較する。
PDF の抽出は1本あたり数十秒かかるので、**抽出を走らせる前に**原典の SHA-256 と
抽出器の版で冪等判定する。冪等でないと `fetched_at` だけが動いて作業ツリーが毎回汚れ、
「再生成しても同じか」を見る CI の判定が意味を失う。**staging 以降は原典だけから何度でも再生成できる**こと。この2つが崩れると、表記ルールを直すたびに全自治体を再クロールすることになる。

## 保管するものと再生成するもの

| 内容 | 保存先 | Git |
|---|---|---|
| 原典 CSV/PDF、取り込み Parquet、証跡 | 非公開 R2、個別の内容ハッシュ | 入力一覧だけ |
| 取得元・階層・金額段階の宣言、分類・名称の判断 | pipeline/ingestion と dbt seeds | 管理する |
| 配布 CSV/FDP/catalog/manifest | release ごとの R2 | 管理しない |
| D1 の検索用表・公開メタデータ | D1 | schema と生成コードだけ |
| 復元済み入力・PDF/OCR キャッシュ | pipeline/.cache/ | 管理しない |
| DuckDB・dbt manifest・検査結果・ローカル報告 | pipeline/build/ | 管理しない |

原典と証跡を公開 Worker へ bind しない。公開済み release の再構築に必要な入力を保持し、配布物の cleanup に連動させない。既存 data/ は遠隔保管・復元を確認してから tracking を外す。

**団体の同一性（名称・ocdId）は `packages/jurisdictions/jurisdictions.json`。**
①②③すべてが同じキーで束ねるので、どれか1層のファイルに同居させない。
⚠️ 以前は③会議録のゲート判定ファイルに同居しており、**予算の粒度調査が母集団を得るためだけに③のファイルを読んでいた**。
設計上は分離していたのに、③が落ちたら①も動かない状態だった。

⚠️ **この文書と `jurisdictions/` の実測の主張は、調査スクリプトの観測から出ている。**
観測は commit しないので、主張には実測日を添え、
再確認するときは該当スクリプトを回して観測を取り直す。

## パーサ設計の原則

自治体の公開資料を横断して構造化した別 PJ の実測から得た原則。**driver を1本も書く前にここを決める** — どれも後から変えると配布済みの成果物が壊れる種類の決定で、公共財として配る以上その破壊は外部に波及する。

**1. id は出現順の連番にしない。中身由来の安定キーにする。**
連番はパーサを直すたびに全体がずれる。実測で、パーサ修正をまたいで同じ対象を指し続けた id は**連番だと 6.6%、中身由来キーなら約95%**だった。fudoki は SayIt に倣って**発言単位の permalink** を出す＝ **id は公開 API の一部**なので、連番を採ると表記ルールを1つ直すだけで permalink が全滅する。Speech の id は `(団体コード, 会議日, 会議体, 話者原文, 本文ハッシュ)` のように中身から導出し、衝突したときだけ連番を足す。

**2. 構造を潰さない。**
フラットな列に潰すと文脈が落ちる。予算資料を事業の一覧に潰すと「どの款・項の下か」が消えて後段の分類が効かなくなるのと同じで、会議録を1次元の発言列に潰すと「どの議事日程・どの議案に対する発言か」が落ちる。Popolo の Speech は event に属し、Akoma Ntoso は debateSection を入れ子で持つ。**Load 段で階層を保ったまま中間表現にする**（潰すのはいつでもできるが、復元はできない）。

**3. 資料名ではなく中身の粒度で判定する。**
名前が有望な資料が使い物にならないことがある（「予算概要」「予算要求状況一覧表」はどちらも款項レベルの集計で、事業名が1つも載らない）。会議録でも「全文記録か要点記録か」はサイトの表記と一致しないことがあるので、`transcript.recordType` はページの文言ではなく**実物を見て**埋める。同じ判断は `SchemaCheck` で既に採っている（データセット名ではなく列構成で判定する）。

**4. 母集団の誤りは後段の精度改善では救えない。**
「一部だけを収録した資料」を母集団にすると、パーサをいくら直しても recall は原理的に出ない。分類の問題ではなくソース選択の問題だから。fudoki で対象になるのは `gate.fetch === 'allow'` の17団体だけで、東京最大勢力の DB-Search 23団体と都議会が丸ごと外れている。**この状態で「東京62団体を横断」と言うと同じ誤りになる**ので、カバレッジは主張ではなく成果物に数値で同梱する。

**代表1件は母集団ではない。** manifest の `openData.budget` のような「団体ごとの代表」を全体だと思って測ると、結論が反転する。実際に `check:fiscal` の初版はこれで「事業単位のデータは0件」と誤判定した（代表1件がたまたま指標表だっただけで、同じ団体が28件のデータセットを持っていた）。**「無い」と言う前に、探し方が母集団を張れているか**を疑う。

**検索クエリも母集団ではない。** その次の版は全文検索のクエリ語で候補を集めており、
予算資料を持つ17団体のうち8団体しか見えていなかった。**しかも形式で CSV に絞っていた**ので、
XLSX / XLS でしか出していない9団体が「予算データ無し」に見えた（2026-08-30 実測）。
どちらも「見つかったものの中で正しく判定する」問題ではなく、**見に行っていない**問題である。
いまは団体ごとに全データセットを列挙する。**取りこぼしの3つの入口は、
母集団・形式・語彙**（事業階層の推定語に「細目」が無く、多摩市を1年近く落としていた）。

**5. 例外は一般化せず、その対象に閉じる。**
レイアウトの差を「全対象共通の一般ルール」に昇華しようとすると他を壊す。実測では一般化案を3つ試して**3つとも他自治体を悪化させた**。driver は systemFamily 単位で切るが、**同一ベンダー内の個体差は jurisdiction 単位のフラグで局所に閉じる**。そのために全対象の before/after を毎回比較する回帰チェックが要る（悪化は必ず「直したつもりの変更」から来るので、都度回さないと検出できない）。

**6. 捨てる判断は加点に変える。**
条件に合わないものを除外する hard filter は「1件を救うために正解を大量に落とす」典型的な失敗をする。話者の名寄せでも、照合できない話者を**捨てずに confidence を付けて残す**。捨てた瞬間、下流にはその発言が存在しなかったことしか伝わらない。

**7. 一次レスポンスは全部保存する。**
後から欲しくなった項目を取り直すより、最初に丸ごと持つ方が安い。raw + provenance で既に採っている型（原文 + 取得URL + HTTP status + SHA-256 + 取得時刻）を Extract 全体に適用する。

### 測れる状態を先に作る

上の 1 と 5 は、**測っていなければどちらも「直ったつもり」で終わる**。driver と同時に次の2つを用意する。

- **id 生存率**: パーサ変更の前後で、同じ発言を指し続けた id の割合。1 の 6.6% / 95% はこの指標で出た数字で、CI で回していなければ気づけない
- **発言分割・話者同定の正解セット**: 人が手で付けるしかないので、**ラベルを付けられる形（UI なり JSON なり）を用意する側に倒す**。ここを自動化しようとして止まるより、人が1時間で100件付けられる導線の方が早い
