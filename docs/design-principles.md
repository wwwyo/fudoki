# 設計方針・対象・パイプライン・パーサ原則

構造・標準・配布・分類の判断を変えるときの正本。
決定の記録は `docs/adr/`。

## 設計方針

**1. 独自スキーマを発明しない。ただし1本の標準に全部を載せようとしない。**
標準に載ること自体が相互運用性の主張であり、自作すると必ず既存ツールから外れる。予算・決算は Fiscal Data Package、調達は OCDS を使い、標準が規定した場所で繋ぐ。

| レイヤ | 標準 | カバーするもの |
|---|---|---|
| **① 何にいくら** | [Fiscal Data Package 1.0.0](https://fiscal.datapackage.org/) | 列を **fiscal concepts（ColumnTypes）** で意味づける（コロン区切りの階層。例 `administrative-classification:generic:code`）。全要素が任意。予算は **Budget Standard Taxonomy**、支出実績は **Spending Standard Taxonomy**。**Budget 側に COFOG（`functional-classification:cofog:division:code` 等）と GFSM の列型が定義済み**で、分類表を自作しなくてよい |
| **② いつ何が公告されたか** | [OCDS](https://standard.open-contracting.org/latest/en/schema/reference/) | 調達プロセス全体（planning → tender → award → contract → implementation）。Apache 2.0 / JSON Schema。**ただし官公需 API が埋めるのは tender まで**（後述） |

継ぎ目:

- **① ↔ ②** — OCDS の `planning.budget` が `id` / `amount` / `projectID` に加えて **`uri`＝機械可読な予算データへのリンク**を持ち、仕様が FDP との連携を明記している
- **事業者の同一性** — OCDS の `parties`。ただし**官公需 API に事業者は載っていない**（下記）ので、この継ぎ目は現状つながっていない

⚠️ **参照先を間違えないこと。** FDP の現行は `fiscal.datapackage.org` の **1.0.0**。
前身（0.3.0）や旧サイト（1.0-rc.1）を現行と誤読しない。`profile: "tabular-data-package"` は
正しい値で、**「これは FDP である」を宣言する口は仕様上どこにも無い**ので `fudoki.specification`
を版の宣言として持つ。この事実は配布物に書かない（利用者のすることが変わらない）。

⚠️ **採用した標準のうち FDP の更新が止まっている**ので、
「止まったら自分で維持する」は保険ではなく既定の運用（方針3）。
FDP 採用自体は変えない（予算の事業別明細を対象にする現役の代替が無い）。
実測の根拠は `docs/fdp-spec-notes.md`。

**分類 dimension は 款→項→目→節 と COFOG の2本を張る。** COFOG 写像は後付け機能ではなく一級の要件で、自治体間比較にも将来の国際比較にも同じ写像が効く。後回しにすると両方作り直しになる。

**COFOG も階層である**（division 01 → group 04.5 → class 04.5.1）。
規則は**決まった粒度をそのまま `cofog_code` に持つ**（`01` / `04.5` / `04.5.1`）。
⚠️ **division / group / class を別々に宣言しない** — 同じ事実が3箇所へ分かれ、
粒度を下げたときに片方だけ古くなる。配布物では分解して3列で出すが、宣言は1つである。
⚠️ **粗い粒度は誤りではない。** 款の名称だけで決まる規則（総務費 → 01、民生費 → 10）は
division 止まりが正しく、group を埋めるには項や目まで下げる判断が要る。
**空は「該当が無い」ではなく「まだ降りていない」**を意味する。

**2. 特定自治体向けサイトではなく汎用層として作る。**
団体ごとの差は宣言に置き、取得・変換・配布の処理を再利用できる形にする。「他自治体でも動く」を口約束ではなくコードで示す。

**3. 運営者が消えても止まらない形にする。**
先行事例は3つの死に方をした。**個人運営は消滅**（chiholog は798自治体を横断検索していたが現在 DNS ごと消えている）、**会社運営は無料枠の線引きを握られた**（Open States は Plural に買収後、非商用のみ無料・GraphQL v2 はサンセット）、**標準そのものが止まった**（Fiscal Data Package は 2024-03 を最後に更新なし）。**正本**をリポジトリに置き、CI で更新し、fork 可能にする（コードは MIT）。

⚠️ **ライセンスは1つに畳めない。** コードは fudoki のものだが、原典と正本は各自治体のもので、
**持っていない著作権にライセンスは与えられない**。root の `LICENSE`（MIT）を data/ まで及ぶと読ませると、
CC BY が求める帰属を下流が落とす。層ごとの宣言は `data/LICENSE` と各 `datapackage.json` にあり、
原典のライセンスは団体ごとに `ingestion/budget/sources.toml` が持つ。
判断のリソースを CC BY 4.0 にできるのは原典が継承を求めないからで、CC BY-SA の団体が入れば
その選択は成り立たなくなる（`fdp/build.py` が停止する）。
⚠️ **原典が1種類とは限らない。** 事業名を市サイトの決算資料 PDF から起こしている団体があり、
そちらは再配布の可否が未確定である。配るのは抽出した事実で、事実に原典のライセンスは付いてこないが、
`sources` と `fudoki.factsFrom` に**出典としては書く** — 利用者が列の出所を辿れる必要がある。

**正本はリポジトリ、API やダッシュボードはそこから生成する派生物**、という向きを崩さない。API を出すこと自体は歓迎する（Open States は bulk download と API を併存させ、ProZorro は公開 API と分析ダッシュボードを分離している）。**やらないのは配布を API 単独にすること** — 自前で CKAN 等を運用する形にすると、そのサーバが止まった時点で chiholog と同じ死に方をする。repo に置けば版が git 履歴に残り、「いつ時点の正本か」も追える。

**ダッシュボードは `https://fudoki.dev/` で配信する。** これは派生物であって正本ではない。
画面が止まっても配布物は repo に残る、という向きが保てる限りドメインを持つこと自体は問題にならない。
配布物の絶対 URL（`canonical` / `og:image` / `sitemap.xml`）はこのドメインを指す。
⚠️ **ルートパス（`https://fudoki.dev/`）で配信する前提**なので、`vite.config.ts` の `base` は `/` のままでよい。
`base` に効くのは**パス**であって DNS 名ではない。`www.fudoki.dev` のようなサブドメインへ移しても `/` のまま。
サブパス（`example.github.io/fudoki/` のような形）へ移すときだけ、`base` と上記3箇所を同時に変える
（片方だけだと静的アセットが 404 になる）。
置き場は Cloudflare。apex をそのまま向けられるのは Cloudflare が CNAME flattening をするからで、
`CNAME` ファイルは要らない（GitHub Pages なら要る）。

配信は **Cloudflare Workers の静的アセット**（`apps/web/wrangler.jsonc`）。`main` を持たない
アセットだけの Worker で、画面はサーバ側で何もしないのでスクリプトは置かない。

⚠️ **ホスティング側でビルドさせることはできない。** 画面は `pipeline.json` と `preview/` を読むが、
どちらも commit していない（再実行で得られるローカル生成物）。生成には `bun run report` が要り、
それは `dbt/target/manifest.json` を読むので、**dbt を回さないと画面のデータが存在しない**。
clone しただけの環境では作れないため、Git 連携でホスティング側にビルドさせる構成は採らない。
手元で組んでから投げる。

```bash
bun run deploy:web    # dbt → report → vite build → wrangler deploy
```

⚠️ **`deploy:web` が dbt から通しているのは、古い `dist` を黙って上げないため。**
`wrangler deploy` だけを叩くと、手元に残っている前回の `dist` がそのまま公開される。

`apps/web` の運用ハマりどころ（デプロイ後の確認方法・`DESIGN.md` に何を書くか）は
`.agents/skills/web-frontend-ops/`（session-retro が維持）を参照。

`apps/api`（Cloudflare Workers + oRPC）のデプロイ・運用のハマりどころは
`.agents/skills/cloudflare-api-ops/`（session-retro が維持）を参照。

**原典・証跡・配布物をリポジトリに置く。** 原典は Parquet で `data/raw/` へ、取得の単位（団体コード・年度・direction）で partition する。全量（62団体 × 9年度）で 79 MB と実測しており、git repo として普通の範囲に収まる。調査の観測とパイプライン報告は commit しない（再実行で得られるローカル作業ファイル。主張には調査日を添える）。

⚠️ **止めているのは原文の複製であって、配布物ではない。**
再配布可でない取得元（自治体サイトの PDF など）でも、そこから**抽出した事実**は配布物に入る。
ここを混同すると、CSV が無い団体の配布物が丸ごと空になる。
その帰結として `raw/` の保証は取得元ごとに違う（`sources.toml` の `raw_form` が宣言する）。
**権利まわりの整理は [data/LICENSE](../data/LICENSE) が正本**で、ここには要約も置かない。

**配布先として GitHub Releases とオブジェクトストレージは採らない。** Releases はアセットが Git オブジェクトでないので clone にも fork にも含まれず、かつ 1,116 ファイルをアセットとして貼れないため1アーカイブにまとめるしかなく、「1団体分だけ数十 KB 落とす」ができなくなる。オブジェクトストレージは部分取得できるが**運用するサーバが要る**ので、止まった時点で chiholog と同じ死に方をする。

なお最も近い前例の Open States は (州, 会期) ごとに **500以上**のファイルをオブジェクトストレージで配っており、ファイル数が多いこと自体は問題にならない（2026-08-22 実測。ただし現在ダウンロードはログイン必須で、上記「会社運営は無料枠の線引きを握られた」がそのまま観測できる）。

**4. 取得と正規化を分離する（ELT）。**
自治体ごとの表記揺れの吸収ルールは必ず後から直る。原典をそのまま保持して Transform をやり直せることが前提（リポジトリに置く。上記方針3）。詳細は「パイプライン」節。

## 対象

**東京都の全区市町村（62団体）を最初の網羅範囲**とする。識別子は総務省の全国地方公共団体コード（東京都のオープンデータ URL 自体がこの体系。6桁で、チェックディジットを含む）。3レイヤはこのキーで**自治体単位では**束ねられる。予算事業・公告・議案のレコード単位で繋ぐには、別に安定した識別子と写像が要る。

### 実装順は予算 → 調達

| | 経路 | 権利 | 実測 |
|---|---|---|---|
| **① 予算** | 東京都カタログ CKAN / 港区 / BODIK / 渋谷区 DCAT-US。届かない団体は各自治体の予算説明書（PDF）へ | **カタログ経由は待ちなし**（確認した範囲が CC BY）。**PDF は取得元ごとに確認が要る** — 公開されていることは再配布を許すことを意味しない | 目以下に到達した団体を実測で確認（`docs/budget-availability.md`） |
| **② 公告** | [官公需情報ポータル 検索API](https://www.kkj.go.jp/api/) | **待ちなし**（robots 制限なし） | `CityCode` が団体コード、`ProjectDescription` に公告全文。**tender 段階まで**（`docs/kkj-api-notes.md`） |

**予算だけで単体の存在価値は成立する**（「なぜ作るか」）。調達は、予算と公告を結び付ける将来展望にあたる。予算の原典の再配布可否は取得元のライセンスで判断し、`ingestion/budget/sources.toml` の `redistribute` がその宣言を持つ。

**実測の詳細は調査文書へ分離した**（この文書に log は書かない）。

- カタログ・サイト側の網羅調査 → `docs/budget-availability.md`
  （62団体中53団体で目より下に届くことを実測。カタログだけでは17団体）
- 官公需 API のフィールド実測 → `docs/kkj-api-notes.md`
  （tender 段階まで。落札者・法人番号は無い）

## パイプライン

原典を捨てない **ELT**。変換のルールが変わっても再取得しない。取得・取り込みと配布を dbt の外に置き、dbt のモデルは staging → intermediate → marts に分ける。以下は予算の実装であり、調達にもこの責務の分け方を使う。

| 段 | 実体 | 責務 | やらないこと |
|---|---|---|---|
| **ingestion** | Python | 取得元（CKAN / 自治体の公開資料 / 官公需 API）から取り、**無加工**のまま `data/raw/` へ Parquet で落とす。取得 URL・HTTP status・SHA-256・取得時刻を添える | 解釈・整形・結合 |
| **staging** | dbt | 原典と**1対1**。列名の付け替えと型付けだけ | **判断**（分類、名寄せ、推定）。行を増減させること |
| **intermediate** | dbt | 提供用データのための中間処理。金額の円換算、団体間の構造統一、共通科目への対応、COFOG 分類、会計間移転の判定 | 取得・配布パッケージの生成 |
| **marts** | dbt | 利用者が使う列・粒度を確定する。団体別・全年度の CSV を書き出し、原典由来の金額と判断は別リソースにする | 新たな分類規則の適用 |
| **export / 配布** | Python（①は `fdp/`） | marts の CSV に列の定義・出典・利用条件・証跡を添えて配布物を作る。**親への参照を保持**（①=款・項・目・節） | 金額・分類の再計算 |

**dbt の層は「原典別の準備 → 中間処理 → 利用者向けモデル」で分ける。** 判断の有無は層名とは別に記録する。
風土記の staging は判断を含まないので、**原典と突き合わせて検証できる**。
intermediate で付与した分類などは原典由来の金額とは別リソースにする。marts は staging を直接参照する場合と、intermediate を経る場合があり、すべてのデータがすべての層を通るわけではない。

⚠️ **境界はディレクトリ名では守れない。テストで縛る。**
原典との**多重集合一致**が「staging に判断が入っていない」ことの検査になる。
これが落ちたら staging に判断が混ざった合図である。
以前 Load を「中間表現へ」と宣言しながら正規化まで実装していたのは、宣言が守られているかを誰も検査していなかったからで、層を増やしても検査が無ければ同じことが起きる。

以前の core を intermediate、package モデルを marts に移した。モデルの参照名（`core_*` / `pkg_*`）と配布データの形式は維持する。命名の整合性だけのために SQL の参照や報告の問い合わせまで変更することは避ける。決定は [ADR 0009](adr/0009-dbt-model-layers.md)。

**ingestion は冪等**にする（同じ入力なら同じ出力、既存があればスキップ）。
⚠️ **取得元は自治体のサーバである。** 同じ資料を何度も取りに行かない。
取得したものは `ingestion/**/.http-cache/`（commit しない）へ置き、既定で24時間は再利用する。
PDF の抽出は1本あたり数十秒かかるので、**抽出を走らせる前に**原典の SHA-256 と
抽出器の版で冪等判定する。冪等でないと `fetched_at` だけが動いて作業ツリーが毎回汚れ、
「再生成しても同じか」を見る CI の判定が意味を失う。**staging 以降は原典だけから何度でも再生成できる**こと。この2つが崩れると、表記ルールを直すたびに全自治体を再クロールすることになる。

## data/ の中身

**data/ に置くのは、外の世界のスナップショットと配布物だけ**（raw・provenance・packages）。
fudoki が決めた入力（取得先・再配布の可否・団体マスタ）はコードの隣、つまり `ingestion/` に置く。
調査の観測はスクリプトの隣（`ingestion/**/observations/`、gitignore）へ書き出し、
パイプライン報告は `apps/web/public/` へ直接書く（どちらも再実行で得られるローカル生成物）。

| | 何 | 書く | commit |
|---|---|---|---|
| `raw/` | **原典**。Parquet。取得の単位ごとに partition | `ingestion/budget/fetch.py` | ○ |
| raw の隣の `provenance.json` | **取得の証跡**。URL・status・SHA-256・取得時刻・ヘッダ・行数 | `ingestion/budget/fetch.py` | ○ |
| `packages/` | **配布物**。団体ごとに正本と判断を別リソースで | dbt の marts モデル + `fdp/build.py` | ○ |
| `fudoki.duckdb` | 実行時に組む一時ファイル | dbt | gitignore |

**団体の同一性（名称・ocdId）は `ingestion/shared/jurisdictions.json`。**
予算・調達を同じキーで束ねるので、どれか1層のファイルに同居させない。

⚠️ **この文書と `jurisdictions/` の実測の主張は、調査スクリプトの観測から出ている。**
観測は commit しないので、主張には実測日を添え、
再確認するときは該当スクリプトを回して観測を取り直す。

## パーサ設計の原則

自治体の公開資料を横断して構造化するときの原則。識別子や階層の扱いは配布物の利用者にも影響するため、取得・抽出の実装と同時に検査を用意する。

**1. id は出現順の連番にしない。中身由来の安定キーにする。**
連番はパーサ修正による行の増減で変わる。予算明細の識別子は、団体・年度・会計・科目階層など、同じ明細を指す情報から導出する。

**2. 構造を潰さない。**
予算資料を事業の一覧だけにすると「どの款・項の下か」が消え、後段の分類に必要な情報が失われる。取り込みでは原典の階層を保つ。

**3. 資料名ではなく中身の粒度で判定する。**
名前が有望な資料が使い物にならないことがある（「予算概要」「予算要求状況一覧表」はどちらも款項レベルの集計で、事業名が1つも載らない）。実際の列構成や PDF の本文を見て、届いている階層と名称の有無を判定する。

**4. 母集団の誤りは後段の精度改善では救えない。**
「一部だけを収録した資料」を母集団にすると、パーサをいくら直しても recall は原理的に出ない。分類の問題ではなくソース選択の問題だから。風土記が目指す範囲は東京都62区市町村だが、収録済みの範囲とは区別する。収録した団体・年度・階層は配布物と報告で示す。

**代表1件は母集団ではない。** manifest の `openData.budget` のような「団体ごとの代表」を全体だと思って測ると、結論が反転する。実際に `check:budget` の初版はこれで「事業単位のデータは0件」と誤判定した（代表1件がたまたま指標表だっただけで、同じ団体が28件のデータセットを持っていた）。**「無い」と言う前に、探し方が母集団を張れているか**を疑う。

**検索クエリも母集団ではない。** その次の版は全文検索のクエリ語で候補を集めており、
予算資料を持つ17団体のうち8団体しか見えていなかった。**しかも形式で CSV に絞っていた**ので、
XLSX / XLS でしか出していない9団体が「予算データ無し」に見えた（2026-08-30 実測）。
どちらも「見つかったものの中で正しく判定する」問題ではなく、**見に行っていない**問題である。
いまは団体ごとに全データセットを列挙する。**取りこぼしの3つの入口は、
母集団・形式・語彙**（事業階層の推定語に「細目」が無く、多摩市を1年近く落としていた）。

**5. 例外は一般化せず、その対象に閉じる。**
レイアウトの差を全対象共通のルールにすると、他の原典の抽出を壊すことがある。団体・年度・資料ごとの違いは取得元の宣言とレイアウト定義に閉じ、共通処理を変更したときは対象の原典で抽出結果を比較する。

**6. 分類できない行を捨てない。**
共通科目や COFOG に割り当てられない行も、原典由来の金額として残す。分類できなかった状態を別に示し、未分類の金額が集計から黙って消えないようにする。

**7. 一次レスポンスは全部保存する。**
後から欲しくなった項目を取り直すより、最初に丸ごと持つ方が安い。raw + provenance で既に採っている型（原文 + 取得URL + HTTP status + SHA-256 + 取得時刻）を Extract 全体に適用する。

### 測れる状態を先に作る

識別子と抽出規則を変更するときは、次の検査で影響を確認する。

- **識別子の対応**: 変更前後で同じ予算明細を同じ識別子で参照できるか。
- **抽出結果の検査**: 原典の小計・合計との一致を確かめ、抽出器を変更したときは団体・年度ごとの結果を比較する。
