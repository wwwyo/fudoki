# 取り込みコードと既存Parquetの配置移行

確認日: 2026-10-08

## 移動したコードと管理情報

団体固有のコード・宣言を `pipeline/ingestion/fiscal/jurisdictions/<団体>/layouts/`、既存の共通抽出器を `fiscal/layouts/fiscal_general/`、原典登録・収録監査を `fiscal/management/` へ移した。従来の団体ノートは各団体の `README.md` に置いた。移動先一覧は [relocations.json](../../../pipeline/ingestion/fiscal/legacy/relocations.json) に保持する。

旧import・パス参照と対応するconsumerの識別子を更新した。dbtの変更は移動したproviderの識別子と文書内参照の修正であり、モデルの処理は変更していない。旧固定入力を読むC/Fは `sources.lock.json` を継続参照する。この一覧を新しいBから更新する経路と、旧原典領域へのアップロードは停止した。

新しい管理JSONの [schema](../../../pipeline/ingestion/fiscal/manifest.schema.json) と [実行入口](../../../pipeline/ingestion/fiscal/run.py) を追加した。CSVと既存の見開きPDFは共通の変換入口を持つ。既存の他の抽出器は移動先で従来のローカル候補用CLIを維持し、新しい保存はschemaを通る入口から行う。従来の環境や観測を固定した抽出器は、その条件を満たさずに再実行できるとは扱わない。

## 既存表の移行状況

旧入力一覧1,163件のうち824表が、原典SHA・団体・年度・資料区分・補正号・方向について現在の選定に対応する。SHAで重複を除いた原典ファイル247件に対応し、223件の対象別JSONへ保存・登録した。原典の形式による内訳はtext PDF由来741表、scan PDF由来35表、CSV由来48表である。歳出783表・歳入41表を含む。表数は行数や原典数ではなく、観測・検算用の表も含むParquetファイル数である。

| 状態 | 件数 |
| --- | ---: |
| 新しいprivate R2 keyへ保存・登録した表 | 824表 / 223件の管理JSON |
| 登録済み計画のうちR2保存が未完了の表 | 0表 |
| 現在の選定と原典が異なる旧入力 | 165件 |
| 上流の原典選定・保存が未完了の旧入力 | 55件 |
| 対象または補正号が現在の選定と対応しない旧入力 | 4件 |
| 補助入力または方向が未確定の旧入力 | 111件 |
| 同じ会計・同じ役割の別原典で表IDが衝突する旧入力 | 4件 |

移行は `retained` の宣言でingestion後の旧Parquetと同じバイト列を保存する。824表は旧表のSHA・サイズとの一致、ローカルの保存キャッシュ、原典参照、入力fingerprintを再確認した。保存前に行数・列型を取得し、管理情報に登録した。新しい抽出器による原典からの再抽出やC/Dの財政値の再認定を意味しない。

最初の保存は165表でcfのOAuth認証が期限切れになり停止した。2026-10-08に認証更新を確認し、残り640表の保存・登録を完了した。

保留していた23件のID衝突を調べると、19件は明示された会計が異なっていた。既存IDは維持し、追加する表のIDだけに会計の識別を加え、6件の対象別JSONへ19表を追加保存した。schema・対象階層・原典選定・Parquetの値と粒度は変更していない。既存の変換定義の変更や表の削除は認めず、全表の保存成功後に対象別JSONを更新した。

## 別途判断が必要な範囲

保留339件を未完成と一括判定して削除してはいない。完成表や後段が参照する補助入力も含む。次の判断は、今回の移行では行っていない。

- 原典選定と対応しない224件は、別の原典が選ばれている165件、原典の選定・保存が未完了の55件、対象が一致しない4件に分かれる。後者4件には、狛江の2020年度補正9号と、補正号が未確定の昭島の3表がある。既存表を使うために現在の選定を差し替えたり、原典対応の制約を緩めたりはしない。上流で採用原典と対象を確定する必要がある。
- 補助入力・方向未確定111件には、全頁・文字観測・名称マスタ等がある。歳出または歳入の取り込み表へ機械的に割り当てない。新しい補助入力のR2保存境界を定める場合は別途設計する。
- 残るID衝突4件は、多摩の2020年度決算・一般会計の階層コントロールと節の観測表である。同じ会計・役割の別原典なので、会計によるIDの区別では解消しない。分冊として区別するか、どの表を使うかを原典から確認する必要がある。値の一致だけで統合・削除しない。

旧R2領域は削除していない。旧C/Fは `sources.lock.json` が指す `inputs/{origin,table}/sha256/` を読む。旧入力一覧の検査もこのkey形式を要求するため、新keyへ書き換えるだけでは動かない。旧C/Fを新しい対象別JSONから読む入口へ切り替えるかを、別途判断する必要がある。それまでは移行済み表の旧keyも保持する。既存Parquetの保存先移行と、後段の入口の切り替えは別の作業である。

## 再開する

`pipeline/` で実行する。`LEGACY_LOCK` は移行開始時の旧入力一覧、`REPORT` はローカルの結果ファイルを指定する。planだけなら `--remote` を省略し、管理JSONの作成も行う場合は `--write-plans` を付ける。

```bash
bun run ingestion:migrate --lock "$LEGACY_LOCK" --report "$REPORT" --remote --extend-plans
bun run ingestion:check
```

既存の変換設定と計画が違う場合は上書きを拒否する。`--extend-plans` は既存の変換定義がすべて同一のまま、新しい表を追加する場合だけ許可する。表IDの衝突を解消する場合も、現在の保存参照と処理済み・未処理範囲を確認してから計画を変更する。別年度・別方向の領域を掃除しない。
