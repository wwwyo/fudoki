## 1. グローバルの勝ちパターン（分析）

ハッカソンのピッチコンテスト（YC Demo Day / TechCrunch 型 / NASA Space Apps / EU Datathon / 各種 hackathon 審査記録）を横断すると、勝ちは 6 点に集約される。

**① 最初の 15 秒はアーキテクチャではなく「問い」。**
勝者は技術や構成図から入らず、個人的なストーリー・統計・挑発的な問いで始める。wiki の ParlParse 分析（[fudoki.md](../../me/wiki/fudoki/fudoki.md)）と同じ結論が独立に出ている — Public Whip が勝ったのは「議事録を機械可読に」ではなく**「あなたの選挙区の議員は、あの法案にどう投票したか」**という個人に紐づく1つの問いに翻訳したから。**fudoki のピッチにまだ無いのはこの問いだけ**（wiki 自身がそう書いている）。

**② デモが王様。混乱するデモの強作は、理解できるデモの平凡作に負ける。**
審査記録の定番の教訓。「startup pitch に2分使ってデモに1分」ではなく逆。2分動画なら **30〜45 秒をデモ 1 本に集中**し、機能一覧ではなく「1つの具体例が通る」ことを見せる。

**③ 明瞭さは複雑さに勝つ。審査員が評価するのは推論。**
JetBrains の審査員記録: 勝つのは最先端のプロトタイプではなく「問題をどう理解し、何を優先し、なぜその判断か」が伝わるチーム。**判断の理由を1つだけ語る**（fudoki なら「事実と判断を層で分ける理由」が最有力）。

**④ 数字の証拠（traction）を1枚に集約。**
YC 型の定石: 最強の1指標を大きく。fudoki の数字は 2団体・55,255行・9年度・検査42本。**「実装した」ではなく「実測した」**という語りは行政データ文脈で特に効く。

**⑤ Why now を1文で。**
「何が変わったから今できるのか」。fudoki の答えは明確 — **AI が使う側に現れた**。構造化されていないデータは AI が読めず、MCP という配り方が生まれた。

**⑥ 審査基準の語彙に自分から対応づける。**
審査員は rubric で聞いている。5軸（データ活用/アイデア/技術/ソーシャルインパクト/サービスデザイン）の語彙をスライド側が先回りして使うと、採点表に書き写しやすいピッチになる。

2分の標準時間割（hackathon pitch guides の合意 + 日本語 300〜350字/分）:

| 区間 | 秒 | 中身 |
|---|---|---|
| Hook | 0:00–0:15 | 問い（アーキテクチャ禁止） |
| Problem | 0:15–0:35 | 痛みの実在。一次体験があれば最強 |
| Solution | 0:35–0:50 | 何をするかを1文 + 名前の物語 |
| **Demo** | 0:50–1:25 | **1つの具体例が通るところ** |
| Proof | 1:25–1:45 | 数字と、判断の理由1つ |
| Vision | 1:45–2:00 | PoC で終わらないロードマップ |

## 2. 現行スライド（7枚 YC 形式）の診断

| 現行 | 判定 |
|---|---|
| 1 表紙「公開されているのに読めない、を読める形にする。」 | ○ one-liner として完成。ただし **hook（問い）が無いまま Problem に入る** |
| 2 Problem | ○ 「昨年の都知事杯で痛感」の一次体験は勝ちパターン通り。残す |
| 3 Solution + パイプライン図 | △ 図は2分動画では読めない。1文+最小図に |
| 4 Demo 311,000円 | ○ 具体例は正しい。**ただし静止画。動画では実際に引く画面を見せる** |
| 5 Technology 3枚組 | △ 2分では重い。「宣言を1つ書くだけ」の1メッセージに圧縮 |
| 6 AI×MCP | ○ Why now としてそのまま効く |
| 7 将来の展望（3層・Open States） | ○ 方向は正しい。**「誰が変わるか」の一言が無い** |

**最大の欠落は2つ**: (a) 冒頭の問い、(b) ソーシャルインパクトを「人の変化」で言う1文。
どちらも wiki に答えが既にある — (a) は ParlParse 分析の宿題、(b) は「査定の基準が前年比から類似団体比に変わる」（第3波の持論）。

## 3. 狙う賞（推奨）

**主戦: データ活用賞。副戦: 技術賞。物語で都知事杯を射程に。**

- 5軸がそのまま賞名になった今年の構造では「どの軸で勝つか」を先に決められる。fudoki は作品の性質上、データ活用（オープンデータの扱いの深さ: 出典・ライセンス・原典保持・団体差の実測）と技術（層の分離・検査・標準準拠）が最も強い
- 2025 審査員の芯（行政実装性・相互運用性・出典/ライセンス厳密・PoC止まりにしないロードマップ）は全部 fudoki の設計思想と一致している。**背伸びせず、既にやっていることを審査の語彙で言うだけでよい**
- ソーシャルインパクトは「市民監視」に寄せない（wiki の供給戦略: 告発から始めると発生源が閉じる）。**「自治体が自分の支出を説明できるようになる」という防御的価値**と「査定の物差し」で語る

## 4. 骨子（2分・6ビート）

> 書式: 【秒】ビート名 — スライド ／ **言う一文（ナレーション骨格）** ／ 対応する審査軸

**【0:00–0:15】Hook — 表紙（ロゴ + 問い）**
**「あなたの市が、いじめ対策にいくら使っているか。隣の市と比べてどうか。——今これに答えられる人は、ほぼいません。」**
（西村軸: ストーリーテリング。ParlParse の勝ち筋①「個人に紐づく問いへの翻訳」）

**【0:15–0:35】Problem — 現行2をほぼ維持**
**「自治体の予算は全部公開されています。しかし PDF か、自治体ごとに違う CSV。デジタル庁のダッシュボードも款・項で止まる。昨年この都知事杯に出て痛感しました——使えるオープンデータが、圧倒的に足りない。」**
（アイデア軸: 課題の実在。一次体験）

**【0:35–0:50】Solution — 1文 + 名前の物語**
**「そこで、集めて、同じ様式に編んで、標準形式で配ることにしました。名前は風土記。713年、諸国へ同じ様式で報告させて集めた地誌です。1300年前と同じ構造を、東京の62自治体でやります。」**
（記憶に残るネーミングはそれ自体が storytelling の武器。図は出さない）

**【0:50–1:25】Demo — 実際に引く画面（最重要・35秒）**
**「三鷹市の『いじめ問題対策協議会関係費』——311,000円。教育費の3階層下にある事業単位まで、機械で引けます。そして MCP サーバがあるので、AI に日本語で聞くだけでこれが返ります。」**
- 静止画でなく **fudoki.dev の実画面 + Claude が MCP で答える実録画** を画面共有で通す
- 「狛江市と並べる」1 カットを足す（2団体あることが映像で伝わる）。**実在確認済み（2026-08-24 実測）**: 三鷹「いじめ問題対策協議会関係費」令和6年度当初予算 311,000円 ／ 狛江「いじめ問題等対策推進」2020〜2023年度 執行額 各年 18,400円
  - ⚠️ **優劣・多寡の評価は口にしない**。予算と執行という段階の違い・事業範囲の違いがあり、単価差＝非効率ではない（wiki の逆流予測4）。言うのは「**並べて見えるようになった**」ことだけ。これは供給戦略（告発から始めると発生源が閉じる）とも整合する
（データ活用軸 + 技術軸の入口。**審査時に fudoki.dev が 404 だと全部空振り — deploy が前提タスク**）

**【1:25–1:45】Proof — 数字1枚 + 判断の理由1つ**
**「現在 2 団体・55,255 行・9 年度分。検査は 42 本、1つでも落ちたら配布物を作りません。金額の単位も文字コードも自治体ごとに違う——その差は全部コードではなく宣言に出したので、自治体を足す作業は宣言を1つ書くだけです。」**
（技術軸: 推論を見せる。井原=データ品質/CI、田村=出典・版管理に刺さる）

**【1:45–2:00】Vision — 誰が変わるか + ロードマップ**
**「自治体の予算査定には今、『前年比』しか物差しがありません。事業単位で他の市と並ぶと、物差しが『類似団体比』に変わる。まず東京62団体、そして予算・調達・議会の3層を同じキーで繋ぎます。正本はリポジトリにあり、私が消えてもデータは死にません。」**
（ソーシャルインパクト軸: 人の変化を1文で。サービスデザイン軸: 持続性=3つの死に方への回答。宮坂=PoC止まりにしない、高野=行政実装）

**合計 約660字 ≒ 2分。** 各ビート末尾は 1〜2 秒の間を置く（動画は編集で詰められない前提で録る）。
