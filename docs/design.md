# kotonoha 設計

**日本の地方議会の会議録を、国際標準のスキーマに正規化して、機械が読める公共財として配布する。**

「議事録が読めるサイト」ではない。正規化データを本体として出し、その上に人間向け UI とエージェント向けインタフェースを載せる。名前は古今和歌集の仮名序「よろづの言の葉とぞなれりける」から。

---

# Why

## 問題

**予算がどう決まり、何に使われ、効果がどうだったかを、外から機械的に追えない。**

| | 何が分かるか | 形式 |
|---|---|---|
| 予算書・決算書 | いくら付いたか（**結果**） | 一部 CSV、多くは PDF |
| 事務事業評価 | どう自己評価したか（**自己申告**） | ほぼ PDF |
| **議会会議録** | **公開の応答・争点・説明根拠** | Web で公開・機械可読でない |

会議録の固有価値は網羅性ではなく、**議員と執行部の公開の応答が逐語で残る**点にある。予算書（結果）でも事業評価（自己申告）でも代替できない。

その会議録は公開されているのに機械可読ではない。横断も経年比較もできず、予算科目とも事業評価とも突き合わせられない。**再利用の法的根拠はあるのに、形式が閉じている。**

### 構造的な非対称（実測）

東京都は歳入を CSV で約30年分公開している（主税局・都税収入見える化ダッシュボード、CSV 41本）。一方で歳出＝使い道側は、財務局の「財政のあらまし」が26本すべて PDF、政策評価・事業評価の見える化ボードは CSV 3本だがメタ情報のみ。

**取った金は構造化データで出ているのに、使った金は PDF で止まっている。**

さらに予算は款・項・目・節で組まれ、事業評価は事業単位で書かれる。**両者が対応しない**ことが「使い道が追えない」の技術的な正体で、その対応は人間が読んで繋いでいる。

## なぜ空いているのか

行政は既に**やっている**。町田市の課別・事業別行政評価シートは平成26年度から毎年出ているし、都財務局にも政策評価がある。問題は形式で、全部 PDF。

**主体の不在ではなく責任の分断。**各議会には自分の会議録を公開する責務があるが、**自治体をまたいで標準化し、予算・議案・評価と接続する責務と継続財源を持つ主体がいない。**各自治体は自分の PDF を出して仕事を終える。自分の評価を横串で比較されるインセンティブもない。

民間が作れないのは「評価すること」ではなく「**評価を追える形にすること**」。監査・報道・研究がずっとやってきた領域。

## 先行事例

### 国内

| | 状態 |
|---|---|
| **chiholog**（798自治体の会議録横断検索） | **消滅**（DNS ごと応答なし）。個人による全国クロールが維持できないことの実証 |
| **地方議会会議録コーパスプロジェクト**（小樽商科大・木村泰知ら） | 研究用。NTCIR への参加登録＋覚書＋規約同意が必要。対象は平成23〜27年度。MIT 再配布不可 |
| 国会会議録 | 国立国会図書館が2014年から Web API を提供済み（＝**国政はできている**） |

### 海外

3層に分かれて成熟している。

- **標準**: Akoma Ntoso（OASIS の議会・立法文書 XML）、Popolo（人・組織・発言のデータ標準）
- **市民側の実装**: TheyWorkForYou / SayIt（mySociety, UK）、Open States / Plural Open（US 50州）
- **商用**: FiscalNote（2025年通期売上 $138M・約90%がリカーリング）、Quorum（50州+7,000超の自治体）、LegiScan

**ただし英米の先行事例はすべて bill tracking であって budget-outcome tracking ではない。**「予算がどう決まり、何に使われ、効果がどうだったか」は繋いでいない。**そこは世界的に空白。**

日本は標準も市民側の実装も存在しない。**国政は NDL の API があるのに、地方は無い。**

## 誰のためか

1. **都民・市民** — 自分の区から取られた税が何に使われたかを追える
2. **AI エージェント** — 機械が読める形で行政の一次情報にアクセスできる
3. **企業・研究者・記者** — 予算の議論を機械的に追える

## 出口の例: 案件検知（Demo Day 以降）

「予算の過程が追える」ことの応用例の一つ。

日本にロビイング市場はほぼ無いので米国型（FiscalNote / Quorum）は成立しない。成立しているのは入札情報サービスで、NJSS（うるる）は月額57,600円から、収集は週3回の人力。

**ただし会議録は案件検知の一次ソースには向かない。**[自治体調達ライフサイクルの分析](../../me/wiki/knowledgework/local-gov-sales.local.md)から:

- 調達は 予算要求 → 予算成立 → 仕様検討 → **公告** → 入札 → 落札 → 契約 と進み、**公告の時点で仕様と関係が固まっている**
- **契約議案（工事請負契約など）は落札後の議決**＝下流情報
- 予算要求書は**内部文書**で外から見えない
- 法定公表義務は「予算の要領」までで**款項レベル、事業名が出ない**
- **「新規及び主要事業一覧」（任意公表）が事業名・担当課・事業費・財源内訳を持ち、案件同定に足りる**
- シグナルは定例会の年4回しか更新されないので**四半期バッチで足りる**

会議録が持つのは金額や事業名ではなく**争点・根拠・答弁**であり、**予算資料と機械的に接続して初めて効く**。これは kotonoha の設計と整合する。

Demo Day までに測るのは発注到達率ではなく、**予算資料だけでは見つからず会議録によって追加で見つかった案件数・公告に対するリードタイム・根拠が「検討します」以上だったか**。

## 法的根拠 — 取得と再配布を別のゲートで判断する

**取得してよいこと（robots・技術）と、正規化して公開してよいこと（著作権・規約）は別問題。**混ぜると「robots がクリアだから公開してよい」という誤りになる。manifest の `gate` はこの2つを別フィールドで持つ。

| 層 | かかるゲート | 現在の判定 |
|---|---|---|
| **robots.txt** | fetch | ベンダーごとに全面 Disallow / 部分 Allow / 制限なし。**17団体が allow、16団体が review、29団体が deny**（後述） |
| **技術的到達性** | fetch | CDN が UA で拒否する例がある（東村山市） |
| **著作権** | redistribute | **未確定。**40条1項を主要な候補根拠としているが、下記が未処理 |
| **利用規約** | redistribute | 実物を3件確認（東京都議会・品川区議会・相模原市議会）。同型の定型文で「著作権法上認められた場合を除き」と除外しているが、**3件から62団体への一般化は成立しない** |

**現時点で `redistribute: allow` の自治体は0。**取得できることは公開できることを意味しない。

### 著作権が未確定である理由

> 40条1項を主要な候補根拠としているが、**発言種別・会議の公開性・非発言部分・配布形態について専門家確認が完了するまで、本文の一般公開可否は未確定**。

40条1項だけでは以下を一括処理できない。

- 課長・部長による事務的説明が「**政治上の**陳述」に当たるか（当たらないなら2項の狭い枠＝報道目的での新聞・雑誌掲載か放送）
- 非公開委員会、公開性が確認できない会議
- 会議録中の**名簿・見出し・添付資料・引用文**など、発言そのものではない部分
- ベンダーが編集・構成したデータベースや画面の**編集著作物性**
- 著作者人格権、出所表示、訂正・削除、プライバシー
- 同一人物の検索結果が反復的・網羅的に提供され、実質的な発言集になる場合（但書に接近する）

したがって当面やるのは、**fixture を使った研究・変換実験**まで。リポジトリへの全文再配布は別ゲートで、権利確認が済むまで開かない。

### 40条1項の但書でNGになること

条文は「**同一の著作者のものを編集して利用する場合を除き**、いずれの方法によるかを問わず、利用することができる」。NG は1つだけで、**同じ人の発言だけを集めて編集物として固定・配布すること**。趣旨は、その議員が自分の演説集を出す利益を第三者が奪えないようにすること。

| | |
|---|---|
| **NG** | `by-person/<議員>.json` の出力／「◯◯議員の発言一覧」ページの静的生成／発言集としての冊子化 |
| **OK** | 会議単位のファイル（複数話者が混在）／検索での話者絞り込み（**都度の検索結果**であって編集物ではない）／発言単位の permalink |
| グレー | MCP の「この議員の全発言を返す」ツール |

分かれ目は**編集物として固定・配布するか、都度の検索結果か**。正本を会議単位で分割していれば自然に守れる。

⚠️ **mySociety の型をここだけなぞれない。**TheyWorkForYou も SayIt も議員別ページを持つが、UK 法の話であって日本では但書に当たる。



## ライセンスの層 — 根拠が3つに分かれる

混ぜると事故るので分けて持つ。

| データ | 根拠 | 下流へ渡せるもの |
|---|---|---|
| **議会だより CSV**（20団体以上） | **[CC BY 4.0](https://creativecommons.org/licenses/by/4.0/deed.ja)**（明示的な許諾） | **CC BY を継承**して再配布できる |
| **予算・決算 CSV** | **[CC BY 4.0](https://creativecommons.org/licenses/by/4.0/deed.ja)** | 同上 |
| **会議録本文** | **著作権法40条1項**（権利制限規定） | **CC BY とは言えない** |

**40条1項で利用できることと、自分が CC BY で再配布できることは別。**40条1項は「利用できる」と言っているだけで著作権が移るわけではないので、**kotonoha に下流へ CC BY を付与する権限はない**。会議録由来のデータには「出典と、依拠した権利制限規定」を明記して配る。

### ライセンスは CKAN API から機械判定できる

出所は東京都オープンデータカタログ（CKAN）のデータセットメタデータ。**推測ではなく API のフィールドとして取れる。**

```bash
curl -s 'https://catalog.data.metro.tokyo.lg.jp/api/3/action/package_search?q=議会だより&rows=1' \
  | jq '.result.results[0] | {license_id, license_title, license_url, isopen}'
# => { "license_id": "CC-BY-4.0",
#      "license_title": "クリエイティブ・コモンズ 表示（CC BY）",
#      "license_url": "https://creativecommons.org/licenses/by/4.0/deed.ja",
#      "isopen": true }
```

**`isopen` が真偽値で入っている**ので、取り込み可否をコードで判定できる。カタログが定義するライセンス一覧は `/api/3/action/license_list` で取れる。

### 実測分布（2026-08-09）

東京都カタログ全 **9,648** データセットのライセンス別内訳:

| 件数 | ライセンス |
|---:|---|
| **9,645** | **CC-BY-4.0**（99.97%） |
| 2 | other |
| **1** | **CC-BY-NC-ND-4.0** |

**NC / ND は理論上のリスクだが実測ではほぼ存在しない。**ただしカタログは `CC-BY-NC` `CC-BY-ND` `other-closed` `notspecified` も定義しているので、**manifest の `license` フィールドは持つ**（ブロッカーにはならないが、混入したときに黙って取り込まないため）。

なお CC は BY / NC / ND / SA の4要素を組み合わせた6種類（BY は必須、ND と SA は排他）。**オープンデータと呼べるのは CC BY / CC BY-SA / CC0 のみ**で、**NC が付くと将来の事業化が塞がれ、ND が付くと正規化そのものができない**。

## 設計方針

**1. 独自スキーマを発明しない。**
人・組織・役職・発言は **Popolo** に準拠。識別子は **OCD-ID 形式**。標準に載ること自体が相互運用性の主張になる。

**2. 特定自治体向けサイトではなく汎用層として作る。**
mySociety が TheyWorkForYou（UK専用）と SayIt（汎用）を分離したから、南アフリカ People's Assembly やフィラデルフィア市議会が再利用できた。「他自治体でも動く」を口約束でなくコードで示す。

**3. 運営者が消えても止まらない形にする。**
先行事例は2つの死に方をした。**個人運営は消滅**（chiholog）、**会社運営は無料枠の線引きを握られた**（Open States → Plural）。データごとリポジトリに置き MIT で fork 可能にし、UI も静的にする。

**4. 生データを捨てない。**
表記揺れの吸収ルールは必ず後から直る。**raw snapshot と決定的な再変換**があること。

## 東京62団体のアクセシビリティ（2026-08-10 実測）

**母集団は東京都内62区市町村ちょうど。東京都議会は含まない**（都道府県議会は別レイヤなので混ぜない）。以下の数字はすべて `src/extract/sources/manifest.json` から生成したもので、手書きしない。

出発点は[地方議会会議録コーパスプロジェクトの全1,788自治体調査](http://local-politics.jp/)（2020年・団体コード付きスプレッドシート）。ホストは移行しているものが多いため現況を叩き直した。

| ベンダー | 団体数 | robots.txt | fetch |
|---|---:|---|---|
| **DB-Search**（大和速記情報センター） | **23** | `Disallow: /` ＋ トップのみ Allow | **deny** |
| **DiscussNetPremium**（NTT-AT） | **15** | `Disallow: /` ＋ `Allow: /tenant/` | **review**（後述） |
| **VOICES/Web** | **10** | 26個の bot UA を名指し拒否。独自 UA に当たるルールは無い | **allow** |
| **own-site**（自治体サイト直） | **6** | 個別 | allow 4 / review 1（東村山）/ deny 1（中央区） |
| **none**（Web 公開なし） | **5** | — | **deny** |
| **kensakusystem.jp** | **3** | robots なし（404） | **allow** |

**取得してよい17団体・照会待ち16団体・取得しない29団体。**

robots.txt は全ホストぶんを実測して**原文を `data/observations/robots.json` に保存している**（要約を持つと RFC 9309 準拠の再判定ができなくなるため）。SHA-256 が一致することで「ベンダーごとに robots が一様」は主張ではなく事実になっている — dbsr.jp の22ホストが同一の75バイト、VOICES の4ホストが同一の1621バイト。

- **DB-Search（23）** — ホストは `www.city.<名>.tokyo.dbsr.jp` に移行済み。品川のみ独自ドメイン
- **DNP（15）** — うち tenantId を実測済みは13。残る2件（東大和市・小笠原村）は tenantId の取得自体が Disallow 経路への問い合わせなので、照会が通るまで空のままにする
- **VOICES/Web（10）** — `voices/index.asp` 系。**独自ドメインでも中身は同一ベンダー**
- **own-site（6）** — 中央区（AI クローラを名指し拒否 → 意図を尊重して deny）、東村山市（robots が 403、CDN が独自 UA を拒否 → review）、中野・世田谷・足立・島しょ

- **DB-Search（24）** — **東京都議会**・千代田・港・文京・江東・**品川**・板橋・八王子・武蔵野・三鷹・府中・小金井・日野・国分寺・国立・福生・**狛江**・東久留米・多摩・稲城・羽村・あきる野・西東京・日の出町。ホストは `www.city.<名>.tokyo.dbsr.jp` に移行済み（20件を実測解決）。**robots は全ホストで完全一様**。都議会と品川のみ独自ドメイン
- **DNP（13）** — 新宿・墨田・渋谷・北・荒川・**練馬**・立川・青梅・昭島・小平・清瀬・武蔵村山・瑞穂町。全13の tenant と tenant_id を実測取得済み
- **VOICES/Web（6）** — 台東・大田・杉並・調布・町田・江戸川。`voices/index.asp` 系。**独自ドメインでも中身は同一ベンダー**
- **kensakusystem（3）** — 目黒・豊島・葛飾
- **その他（14）** — 中央・世田谷・中野・足立・東村山・東大和 ＋ 島しょ8。島しょは WordPress 標準 robots、中野は `Disallow: /giin_detail.html` のみ

### 会議録本文はオープンデータになっていない

東京都カタログを横断検索した結果、**会議録の本文を公開している自治体は0件**（「速記」「発言」は検索ヒット0）。存在するのは:

- **議会だより CSV**（20団体以上・**CC BY**）— ただし中身は発行号のメタデータと**PDF への URL のみ**。本文なし
- 議会の統計（目黒「区議会開催回数」「議決件数」、大田「議員の定数と現員」「開会数と議決件数」など）

**カウントできるもの（回数・件数）はデータになっているのに、何が議論されたかは1件もない。**

議会だより CSV は全国地方公共団体コードが主キーで CC BY なので、**DB-Search 24団体のフォールバック経路**になりうる（粒度は定例会ごとの要約に落ちるが「何が議決されたか」は拾える）。

## 最大のリスク

**基盤と標準を作り込んで、利用者価値の実例が間に合わないこと。**

2分動画で「取得 → DuckDB → Popolo → MCP」を説明しても、審査員には「よくできたパイプライン」にしか見えない。必ず1本完成させるのはこれ:

```
疑問を持つ → 該当発言を発見 → 前後と議案を確認
          → 予算資料の金額・事業と接続 → 原文 permalink で根拠を確認
```

これが動けば裏側が単純でも作品になる。

**第二のリスクは取得の正当性**（robots / 利用規約 / 著作権）が固まらず「公共財として配る」前提が崩れること。現在 `redistribute: allow` は0団体で、**この前提はまだ立っていない**。

**第三のリスクが最も現実的で、いま起きかけている**: **合法的・倫理的に再配布でき、定期更新できる1本の縦切りを確立する前に、62団体の調査・標準・driver へ広げること。**このまま行くと完成するのは「調査は立派だが、本文を安全に公開できず、予算追跡にも届かない manifest」。だから進め方を縦切り優先に組み替えた（後述）。

# How

## 全体像

```
会議録システム（複数ベンダー）
        │  extract : ブラウザ相当の描画で tenant ページを取得（robots 準拠）
        │  load
        ▼
   DuckDB（生に近いリレーショナル・観測用）
        │  ← ここで SQL で実態を観測する（表記揺れの調査）
        │  transform
        ├──────────────▶ data/*.json      正本・Popolo 準拠・git diff が読める
        └──────────────▶ 検索用インデックス  派生
                                │
                    ┌───────────┴───────────┐
                    ▼                       ▼
                 src/mcp                  web/
```

| 段 | 責務 | やらないこと |
|---|---|---|
| **extract** | 会議録システムからの取得。レスポンスを**無加工**で保持 | 解釈・整形・結合 |
| **load** | DuckDB へ。ネストをリレーショナルに展開 | 名寄せ・表記統一 |
| **transform** | Popolo へのマッピング。話者の名寄せ、職名↔氏名の解決、表記揺れの吸収 | 取得 |

**extract は冪等**（同じ入力なら同じ出力、既存はスキップ）。**transform は生データだけから何度でも再生成できる**こと。

## 取得方法 — robots.txt に従う

`ssp.kaigiroku.net/robots.txt`（実測 2026-08-09）:

```
User-agent: *
Disallow: /
Allow: /tenant/
```

**JSON API（`/dnp/search/*`）は `Disallow: /` 配下。叩かない。**

### なぜ「画面を描画して解析する」で回り込まないか（撤回した案）

一度は `Allow: /tenant/` の画面をブラウザ相当で描画して解析する案を採ったが、**成立しないので撤回した**。

- 画面は Allow でも、**描画すると裏で `/dnp/search/*` を呼ぶ**。そのリクエスト自体が Disallow 対象で、実ブラウザを使っても Allow に変わらない
- REP の適用主体は「自動化されたクライアント」なので、**実ブラウザでもスクリプトが動かせば crawler**。「実ブラウザである」ことと「人間が閲覧している」ことは別
- UA も矛盾する。独自 UA を名乗れば CDN に拒否されうるし、Chrome UA を使えば `kotonoha` と名乗っていないので「相手が個別に拒否できる」という説明が崩れる

したがって DNP の15団体は `fetch: review`。**ベンダー（NTT-AT）と議会事務局への照会で許諾が取れたら、描画で回り込むのではなく API を直接使う**——そのほうが筋が通り、サーバ負荷も軽い。

### User-Agent は連絡先入りの独自名を名乗る

`kotonoha/0.1 (+https://github.com/wwwyo/kotonoha)`。ブラウザを騙るのは robots を守る姿勢と矛盾する。既存のブロックリストに該当しないので `User-agent: *` が素直に適用され、かつ**相手が後から kotonoha を名指しで拒否できる**状態になる。拒否の手段を相手に残すことが誠実さの実体。

⚠️ ただし **CDN の bot 対策で独自 UA が 403 になる自治体がある**（実測: 東村山市。独自UA・curl とも 403、ブラウザUA のみ 200）。**実ブラウザで描画すれば通るが、それは対応ではなく回避。**自動実行する以上は crawler であり、名乗りを捨てて通すのは「相手が拒否できる状態を残す」という上の方針そのものを壊す。東村山市は `fetch: review` に置き、照会で解く。

### AI クローラ拒否をどう扱うか — 3つの層に分ける

混ぜると「robots が拒否している」と「相手が嫌がっている」の区別がつかなくなる。manifest では前者が `robots.verdict`、後者が `robots.aiCrawler`、判断が `gate.constraints` に分かれている。

| 層 | 中央区の例 |
|---|---|
| **REP 判定** | 独自 UA に適用されるルールは無い（`User-agent: *` は会議録経路を拒否していない） |
| **発行者シグナル** | `# --- AI・LLM ---` とセクションを切って AI 関連 UA を名指し拒否している |
| **kotonoha 方針** | 意図を尊重して取得しない（`constraints: [publisher-ai-opt-out]`） |

つまり**取得しないのは robots に従った結果ではなく、こちらの判断**。だから照会で解けるし、解くべき。

⚠️ **GPTBot / ChatGPT-User / Google-Extended / CCBot は目的が違う**（学習・ユーザー起点アクセス・検索/生成利用・web アーカイブ）。一括して「AI 拒否」と読むのは粗く、中央区が何を拒否したかったのかは**照会で確かめるのが最も確か**。

⚠️ **CCBot（Common Crawl）だけは判断が割れる。**本来は汎用の web アーカイブクローラだが、そのアーカイブが LLM の主要な学習データ源であるため AI 対策として弾かれることもある。ただし DotBot / SemrushBot / AhrefsBot / MJ12bot と並ぶ**迷惑ボット対策の定型ブロックリスト**の中にある場合は AI 意図と断定できない（VOICES/Web の標準テンプレートがこの形で、東京10団体が該当）。

そもそも robots の仕様上、**UA 指定のルールはその UA にしか適用されない**。kotonoha は CCBot ではないので、適用されるのは `User-agent: *` グループだけ。この軸は「相手が AI にどういう姿勢か」の記録であって、取得可否の直接の根拠ではない。

**恒久的な解決は許諾。**議会事務局（本文の再利用許諾）と NTT-AT（自動アクセスの可否）の両方へ照会する。片方だけでは足りない（議会事務局は本文の権利者だがサーバへのアクセスを許可できず、NTT-AT はアクセスを許可できても本文の再利用許諾者ではない）。**返答はクリティカルパスに置かない。**

## driver はシステム（ベンダー）単位

DiscussNetPremium は1本で約480自治体をカバーする。自治体単位で書くと破綻する。

```
src/extract/sources/
├── manifest.json    団体コード → システム + 接続情報 + 権利判定 + 調査状態
├── dnp.ts           DiscussNetPremium（NTT-AT）
├── voices.ts        VOICES/Web
├── kensakusystem.ts kensakusystem.jp
└── dbsearch.ts      DB-Search（大和速記情報センター）※許諾が取れるまで実装しない
```

**優先順位:**

| 順 | driver | 団体数 | 理由 |
|---|---|---|---|
| 1 | **DNP** | 13 | robots 条件付きだが可。**全国約480自治体に効く**ので汎用性の証明になる |
| 2 | **VOICES/Web** | 6 | **robots がクリーン**。制約なしで取れる |
| 3 | kensakusystem | 3 | robots なし |
| — | DB-Search | 24 | **照会が通るまで着手しない** |

**driver 2本で19団体、3本で22団体**が robots 上クリーンに取れる。

manifest は driver と同じ場所に置く。

**どの自治体がどのシステムかは自動判別できない。**ホスト名がバラバラで（品川 `kaigiroku.city.shinagawa.tokyo.jp` / 世田谷 `kugi.city.setagaya.tokyo.jp`）、同一パターンは他区に展開していない（実測）。人手で登録する。**この調査は並列 agent に分担できる**（1団体1タスク・独立・出力形式固定・機械的に検証可能）ので、62団体ぶんを14日で揃える。

**「調査済み」と「driver 対応」と「取込検証済み」を分けて持つ。**混ぜるとカバレッジの誇張になる。

```json
{
  "131202": {
    "name": "練馬区",
    "source": { "systemFamily": "dnp", "tenant": "nerima", "tenantId": 367,
                "entryUrl": "...", "evidenceUrls": ["..."],
                "identifiedAt": "2026-08-10", "confidence": "confirmed" },
    "access": { "robots": "api-disallowed",
                "terms": "copyright-law-exception-only",
                "license": "none" },
    "status": { "driver": "implemented", "ingestValidated": true, "published": false }
  }
}
```

`access` の3フィールドが判定軸。`robots` は取得可否、`terms` は規約による上乗せ制限の有無、`license` は **CC BY / CC BY-SA / CC0 なら下流へ継承できる**・`none` なら40条1項に依拠（下流へライセンスを付与できない）・`unknown` は未確認。**NC が付いていたら事業化が塞がれ、ND なら正規化そのものができない**ので、ここは取得前に必ず埋める。

`unknown` を正当な値として許容し、**事実（evidenceUrls つき）と推論を別フィールドで持つ**。並列 agent の出力はそのままマージせず、schema を先に固定して二次確認をかける（同じベンダーの別名分類・JS ページを空ページと誤認・規約が見つからないことを「利用可能」と判定、といった揺れが出る）。

団体コードは総務省の全国地方公共団体コードから取る（上記の値は仮）。**東京都のオープンデータ URL 自体がこの体系**（葛飾区 `131229_katsushikaku_symbol.csv`、狛江市 `132195_kessan2023saisyutu.csv`）なので、予算・決算データと同じキーで join できる。

## DiscussNetPremium の性質（実測）

詳細は `.agents/skills/kaigiroku/SKILL.md`。設計に効く点だけ:

- **発言単位に既に分割されており `title` が話者**。ParlParse がやっている発言分割・話者抽出が不要
- **議員は氏名＋役職**（`小泉純二委員長`）、**理事者は職名のみ**（`情報公開課長`）。理事者は**名簿レコードの職名↔氏名対応**で解く。名簿は会議ごとに付くので人事異動をまたいでも会議単位で正しく解決できる
- **話者表記は自治体ごとに違う**（練馬 `小泉純二委員長` / 岡山県 `議長（遠藤康洋君）`）。**取得層は共通、正規化層は自治体別ルール**
- 名簿には開催日時・場所・傍聴者数・**付託案件（議案第◯号）**も入る

## Popolo へのマッピング

| 対象 | Popolo | 備考 |
|---|---|---|
| 練馬区（区域） | **Area** | OCD-ID 形式の識別子＋団体コード |
| 練馬区議会 | **Organization** | `classification: legislature`、`area_id` で Area を指す |
| 企画総務委員会 | **Organization** | `classification: committee`、`parent_id` が議会。`council_type_name1..5` の階層から起こす |
| 会派 | **Organization** | 実データから拾う |
| 議員・理事者 | **Person** | |
| 委員長・委員・課長 | **Post** | 根拠が揃ったものだけ |
| 所属 | **Membership** | 根拠が揃ったものだけ |
| 発言 | **Speech** | `minute_id` 単位でそのまま |
| 付託案件 | **Motion** | 議案第◯号 |

Speech と、その所属を示す最小限（Area / Organization / Person）から始める。**準拠率より「推測で埋めていないこと」を優先する。**

識別子は OCD-ID 形式:

```
ocd-division/country:jp/prefecture:13               東京都（本家に実在）
ocd-division/country:jp/prefecture:13/city:131202   練馬区（本家未登録・こちらで定義）
```

Area には OCD-ID 形式の識別子と全国地方公共団体コードの**両方を持つ**（互換に使えるが同一体系ではないため）。

## 正本は JSON

transform の出口は2つ。

- `data/*.json` — **正本**。Popolo 準拠・**git diff が読める**・fork の実体
- 検索用インデックス — **派生**

正本は「自治体 / 年度 / 会議」の単位で分割する。巨大な単一 JSON にすると、データ量が増えた時点で「diff が読める」という主張自体が崩れる。

## ディレクトリ構造

```
kotonoha/
├── src/
│   ├── extract/
│   │   └── sources/            manifest.json + driver（システム単位）
│   ├── load/                   → DuckDB（観測用）
│   ├── transform/
│   │   └── rules/<団体コード>.ts   自治体別の表記揺れ
│   ├── schema/                 Popolo の型と検証
│   └── mcp/                    MCP サーバ
├── web/                        検索 UI
│
├── data/                       配布データ（正本）
│   ├── areas.json  organizations.json  people.json
│   └── speeches/<団体コード>/<年度>/<会議>.json
│
├── fixtures/                   取得済みの生データ（少数・出典と取得時刻と hash 付き）
├── .work/                      DuckDB・生レスポンス（gitignore）
└── .agents/skills/kaigiroku/
```

`data/` はコードではなく、リポジトリを開いて最初に見えるべきもの。dir 名に標準名（popolo）を入れないのは**読者がデータ利用者**だから。`src/` 側は**読者が開発者**なので ELT の標準語をそのまま使う。

## データ量と再現性

実測で `councils/index`（練馬区・全年度）が **1.1MB**、1会議ぶんが **176KB**。62自治体×数十年で GB 級になるため、生データ全量は git に置けない。

- `data/`（Popolo JSON）を commit — **これが公共財の本体**
- `.work/` は gitignore
- **`fixtures/` に少数の生データを出典・取得時刻・hash 付きで commit する**

## 実装とデモの分担

- **実装**: DNP 共通 driver を作り、複数自治体で汎用性を測る
- **デモ**: 練馬区など東京都内の具体的な予算・議案・発言を見せる
- **manifest**: 東京62団体ぶん揃える。**driver 実装は DNP + 東京の非DNP 1本に絞る**

## 進め方

**縦切りを1本通してから広げる。**62団体の調査は済んでいるので、次に増やすべきは調査の幅ではなく、1自治体で「取得 → 正規化 → 接続 → 更新追随」が閉じている実例。

1. **再配布根拠まで確認できる1自治体を選ぶ** — 現状の第一候補は**世田谷区**（VOICES・robots に該当ルール無し・予決算委まで全文検索）。議会事務局へ再利用許諾を照会し、規約の実物を確認する
2. その1自治体の会議録を**会議単位で取得し、Popolo で再生成する**
3. **予算項目 — 議案 — 発言を1件、証拠つきで接続する**（kotonoha の差別化は「会議録検索」ではなくここ）
4. **訂正・削除・取得元更新への追随を実証する**（一度取れることと、更新し続けられることは別）
5. ここまで閉じてから2本目の driver（VOICES の残り9団体）へ
6. 並行して照会を出す — 議会事務局（本文の再利用許諾）と NTT-AT（DNP 15団体の自動アクセス可否）。**返答はクリティカルパスに置かない**
7. MCP / web

**先に基盤を用意したくなる引力があるが、正本がまだ1行も出ていないので data/*.json を先に出す。**

# Why not — 採らないこと

## 設計上やらない

**JSON API を直接叩かない。**robots.txt が `/dnp/search/*` を拒否している。技術的には認証不要で叩けるが、公共データ・行政協働を掲げるプロジェクトが無視すると、法的結論以前に信頼性を損なう。取得レートを下げても Disallow が Allow になるわけではない。

**議員個人の発言だけを集めて編集した成果物を出さない。**著作権法40条1項の但書「同一の著作者のものを編集して利用する場合を除く」に抵触しうる。話者で絞る検索機能と、話者別に編集した著作物は別物なので、UI 実装時も意識する。

**会議ごとの名簿から期間つき Membership を生成しない。**出席は所属期間を証明しない。観測できるのは「その日その役職で出席した」だけで着任日・退任日は不明。生成すると**標準準拠の形をした誤データ**になる。

**会議録の評価・要約による意味づけをしない。**一次情報の形式変換に徹する。

**音声・動画（議会中継）を扱わない。**

## 技術選定でやらない

**dlt。**採用を一度決めたが、取得方法が JSON API から描画結果の解析に変わったことで価値の中心が消えた。

| dlt の利点 | 本件での状態 |
|---|---|
| ネスト JSON の自動リレーショナル化 | **消えた**。入力が DOM になり、パース結果の構造は自分で決める |
| incremental loading | **効かない**。レスポンスに更新時刻がなく cursor がない（`council_id` / `name` / `postit_count` のみ） |
| schema evolution | **弱い**。自分でパースした構造なので evolution は自分の管理下 |

残るのは「取得済みの会議を覚える」state 管理だけで数十行。Python を足す理由がなくなったので **TypeScript 一本**にする。

**dbt / Meltano / Airbyte / Dagster / Prefect / Airflow。**

| | 理由 |
|---|---|
| dbt | warehouse + SQL 前提。transform の中身が日本語の話者表記の正規化でありSQLでない |
| Meltano / Airbyte | インフラが要る。git ベースの静的ビルドと合わない |
| Dagster / Prefect / Airflow | オーケストレータが解く問題がまだ発生していない |

先行事例の Open States も汎用 ELT 基盤ではなく **spatula** という小さい自前ライブラリを選んでいる。ParlParse も自前（`pyscraper/`）。

**monorepo の package 境界。**npm publish しない以上、workspace・型共有・ビルド順序の管理コストに見合わない。実際に独立した利用者が現れてから package 化する。

**公式 Popolo JSON Schema との突合。**Popolo の定義と同じ形にしてあれば二重検証は冗長（公式は JSON Schema draft-03 で ajv 等が素で読めず変換が要るという事情もある）。型は自前で定義し、フィールド名・構造を仕様どおりにする。

**OCD-ID の upstream への PR。**形式に合わせておくだけでコストはほぼゼロで、後から本家に載っても衝突しない。

## 期間内にやらない（Demo Day 側へ）

npm publish（schema / MCP）・DuckDB-Wasm・Parquet 配布・CI での差分更新・Akoma Ntoso 完全準拠・transform の関係解決を SQL へ寄せること。

**Data Package（frictionless）**も後回し。ただし CKAN 拡張で `datapackage.json` を生やせるため、東京都カタログ（CKAN）に載せる将来の価値は残る。`data/` が出てから戻る。
