# 狛江市（132195）

2018〜2023年度 決算。東京都カタログ CKAN の「決算書歳出データ・決算書歳入データ」
（款 / 項 / 目 / 大事業・中事業・小事業 / 節 / 細節 / 細々節 / 所属 / 予算額 / 執行累計 / 執行率）を収録。
事業名と科目名は市サイトの決算資料 PDF から解決している（下記）。

実測は `bun run survey:structure 132195` の出力
（`ingestion/budget/observations/132195-budget-structure.json`）。
**観測は commit しない**ので、この文書の主張は 2026-08-22〜23 実測の値である。取り直すときはスクリプトを回す。

## 構造の粒度と意味の粒度は別物だった

オープンデータ CSV は事業階層（大事業）まで届いているのに、
**款・項・目・大事業に名称の列が無い**（数字コードだけ）。CSV だけでは
「いじめ問題等対策推進にいくら付いたか」に答えられない。

名称は**市が公開している決算資料 PDF にある**（カタログには無い。2026-08-22 に
399 データセットを全件走査して確認）。

### 事業名（大事業）

PDF は大事業コードを書いていないので、**同じ目の中で金額が一致するものを対応づける**ことで結んだ。
結果、**PDF がある範囲（一般会計 × 2020〜2023）では金額のある大事業の 98.2%**（金額で 92.2%）に名前が付いた。
⚠️ **配布物ぜんぶで見ると 57.1%**（金額で 43.1%）。範囲を書かずに 98% だけを言わないこと。

⚠️ **これは判断であって、自治体が言っていることではない。** だから正本と別のリソース（`project_names`）に出し、
パッケージの `modifications` に「原典に無い事業名を起こして対応づけた」と書く。
⚠️ **一般会計にしか付かない**（PDF の事項別明細が一般会計だけ。特別会計は款レベルの推移表しかない）。
⚠️ **2018〜2019 には付かない**（市の決算ページがその2年度だけ存在しない）。
⚠️ **金額が 0 の事業には付かない**（同じ目に何件も並んで金額で区別できない）。

### 科目名（款・項・目）

同じ PDF の見出し（`１. 議会費` の形）から解決した（`core_budget_account_names`）。

⚠️ **当初「項・目の名称は決算書 PDF にもコードしか無い」と結論していたが、誤りだった。**
抽出器が科目の欄から数字だけを拾い、その後ろに続く名称を捨てていた。
自分の抽出結果の欠落を資料の性質だと読み替えたもので、原則3（資料名ではなく中身で判定する）の違反。
**「無い」と書く前に、見ていないだけではないかを疑う。**

- 名称は次の行へ折り返す（`１.保健衛生` + `総務費`）。繋がないと実在しない科目名になる
- 継続ページの見出しはコードだけを繰り返す。同じコードなら名称を持ち越す

## 原典の癖（実測）

- **列があることは使われていることを意味しない。** カタログの列構成には
  「大事業・中事業・小事業」が並ぶが、**中事業・小事業は6年度 13,461 行すべて `0`**。
  歳出の細節・細々節、歳入の細々節も同じ。実際に使われている事業階層は大事業の1段だけ
- **階層だけでは行が一意にならない。** 所属（部課）と予算区分（現年度・繰越明許・事故繰越）まで
  含めて初めて一意になる（2023 歳出 2,224 行が階層だけだと 1,855 通りに潰れる）。
  宣言（`budget_extra_key_columns`）を落とすと budget_line_id が衝突する
- **決算書は1行が複数段階の金額を持つ。** 歳出は予算額 / 予算計 / 執行累計。
  FDP は `value` の列型を1つしか持たないので、package 段で段階ごとの行へ展開する。
  主キーも `(budget_line_id, phase_id)` になる。`予算計 = 予算額 + 充流用等増減額` は全行で成立した
- **「予算額」は当初予算ではない。** 補正まで反映した後の額で、当初予算と並べても同じ段階の比較にならない
- **同じリソースの中で単位が割れる。** 歳入の予算現額だけ千円で、他はすべて円
- **文字コードが年度で変わる。** 2018〜2021 は UTF-8（BOM 付き）、2022〜2023 は CP932
- **同名のデータセットが2件あり、中身が違う。** 2018〜2021 は `/komae/R05/` と `/komae/` に
  同名で SHA-256 の違うものがある（所属名称の改称、執行率の `-` と `****`）。R05 側が新しい。
  先頭を採る実装だと CKAN の並びが変わった日に配布物の中身が入れ替わるので、
  複数当たったら止めて `resource_url_contains` の宣言を要求する
- **歳出の予算計と歳入の予算現額は年度・会計別に一致した**（6年度 32 対）。
  歳入が千円単位なので円未満は原理的に合わない（差が出たのは2対、いずれも 1,000 円未満）
- **公共下水道特別会計は 2020 年度から原典に現れない**（公営企業会計へ移行）
- 2020年度に節のコードが振り直されている（`label_column_determines_level` が年度ごとに見る理由）

## COFOG

- **解像度は年度で違う。** 決算書 PDF から科目名を解決できる一般会計 2020〜2023年度は
  項・目まで決まり、分類不能は金額で 5〜6%（ほぼ会計間の繰出）。
  PDF の無い 2018〜2019年度と特別会計は款のままで 25% 前後が残る。全体では 11.4%
- **分類不能と対象外を畳まない。** 公債費の元金償還は「対象外」、利子は 01.7 で「割当済み」。
  名称を解決できた年度は区別でき、2018〜2019年度だけ「分類不能」に残る
- **割当の粒度は group まで 44%、class まで 3%。** 残りは division 止まりで、
  款の名称だけで決まる規則がそれにあたる。**空は「該当が無い」ではなく「まだ降りていない」**。
  学校教育は3本に割れている（教育総務費 → 09.8 / 小学校費・幼児教育費 → 09.1 / 中学校費 → 09.2）
- **会計間の繰出・繰入を消去していない。** 目の名称を解決してもなお繰出先が分からず
  （社会福祉総務費・老人福祉費・再開発費であって受け皿の会計名を含まない）、
  都繰入金が一般会計繰入金と同じ款に同居する。推測して消去するより残すほうを採った（原則6）。
  ⚠️ **全会計合計は会計間の移転を二重に含む**（一般会計の繰出金は6年度で 191 億円）

## 科目マスタとの対応

- 款コードは `1`〜`13`。**法定とずれる** — 災害復旧費（法定11）を持たないため、
  11 公債費→法定12、12 諸支出金→法定13、13 予備費→法定14。
  ⚠️ 当初「款コードは法定の款番号と一致する（実測で裏づけた）」と主張していたが誤り。
  裏づけは款の中身の整合であって、番号の対応の確認ではなかった
- 項「道路橋りょう費」はマスタの「道路橋りよう費」と拗音の大小の表記差（`account_map.csv` に明示）
- 「幼児教育費」「基金費」は法定の項に無い。`kind=addition`

## 未確定

- **款別の公表資料と突き合わせていない。** 書き写せる資料をまだ見つけていない。
  現状の根拠は原典の内部整合（歳出と歳入の一致）だけで、外部からの裏づけではない
- **`adjusted-before-transfer` は fudoki が宣言した予算段階。** FDP の慣行
  （proposed / approved / adjusted / executed）に該当が無い（「予算額」は流用・充用を反映する前の額）。
  `phase:id` は仕様上ただの文字列なので適合するが、他の実装がこの id を知っているわけではない

## 歳入の科目

**歳入は科目の名称の出所がまだ無い。** 原典 CSV に名称の列が無く、
決算資料 PDF（歳出事項別明細）は歳入を載せていない。科目コードのカタログとしては
`account_names.csv` に入るが、名称もマスタ対応も null のまま。
歳入の款コードも法定とずれている可能性が高く（歳出で実証済みの詰まり方）、
名称の根拠なしにコードで対応づけることはしない。
市の決算資料に歳入の事項別明細があれば、歳出と同じ経路で解決できる（未調査）。

### 歳入の科目名の解決（2026-08-24）

決算ページに**歳入事項別明細**が各年度ある。ただし経路の性質が年度で割れる。

| 年度 | 形 | 結果 |
|---|---|---|
| 2023 | 決算資料 PDF（歳出と同一文書 p20〜37）にテキストあり | **79目/22款すべて解決。調定額が CSV と 79/79 一致** |
| 2020〜2022 | 別 PDF。**文字がアウトライン化**（Tj が無くグリフが曲線。テキスト抽出が原理的に不成立） | OCR（llama.cpp + GLM-OCR）で 6〜8割。**名称にはまだ使わない**（下記） |
| 2018〜2019 | 決算ページ自体なし | 解決不能 |

**経路は宣言せず、ページごとに実測で決める（2026-08-29 に変更）。**
以前は `sources.toml` が文書単位で `mode = "text" / "ocr"` と宣言していたが、
原則3（資料名ではなく中身で判定する）と逆を向いていた。いまは抽出器が
ページごとにテキスト抽出を試し、**表の行が取れなかったページだけ** OCR へ落とす。
実測（2026-08-29）では 2020〜2022 が 19/19 ページとも OCR、2023 が 18/18 ページとも
テキストで、宣言と一致した。ただし判定の材料は変わった —
`pdftotext -bbox-layout` は 2020〜2022 の PDF で **SIGABRT で落ちる**ので、
`pdftocairo` で再蒸留してからやり直す。再蒸留すると p1 だけ3語（「（1）歳入」）取れるが
表の行は0なので OCR へ落ちる。**文字数で判定していたらここを取り違えた。**

### OCR を Tesseract から llama.cpp + GLM-OCR へ替えた（2026-08-29）

原典 CSV の調定累計と目単位で突き合わせた結果（一般会計）。

| 年度 | 原典の目 | 抽出した行 | **コードも金額も一致** | 旧（Tesseract）で一致 |
|---|---|---|---|---|
| 2020 | 81 | 52 | **48** | 0 |
| 2021 | 80 | 62 | **60** | 5 |
| 2022 | 81 | 57 | **44** | 1 |

⚠️ **一致率が上がったのは読字精度だけの話ではない。** Tesseract は款コードを
巻き戻していたので、金額が読めても行のキーが合わなかった（2022 は 52 目のうち
40 目がキーは合って金額が違い、1 目しか一致しなかった）。GLM-OCR は表を HTML で返すので、
**罫線の格子から段（款・項・目）が読める**ようになったのが効いている。

- **ページ全体を1枚で渡さない。** 渡すと値は正しく読めるが表の格子が潰れ、
  科目の3段が2列に畳まれて款と項と目が同じ列に並んだ。
  **科目欄と調定額欄だけを切り出して1枚に横へ並べる**と格子が忠実になり、
  画像が小さいぶん速い（実測: ページ全体 39.8 秒 → 切り出し 15.5 秒）
- **段は列だけでは決まらない。** 上の行から伸びた rowspan の都合で1段浅く出ることがある。
  列が言う段を**番号の連続**（款は kan+1、項は kou+1、目は moku+1）で検証し、
  合わなければ番号が続く段へ倒す。倒し方を「常に深いほう」にすると項が目に化け、
  「常に浅いほう」にすると目が款に化けて以降の款番号が全部ずれた（実測で 41/81 まで落ちた）。
  **列に近いほう、同点なら深いほう**が3年度とも最良だった
- **取りこぼしは3〜4割ある。** 科目欄が疎なページ（節の行が続き、目の名前が2行に
  折り返しているページ）で、モデルが科目の列を丸ごと落とすことがある
  （実測: 2020 の p13 は5つの目を1つも返さなかった）。
  ⚠️ **科目欄だけを単独で OCR すると同じページでも5つとも読める。**
  2パスに分けて突き合わせる案は、行の対応づけが別の失敗を招くので採っていない
- 誤読の残りは異体字（`譲` → `讓`、`雑` → `雜`）が中心で、数字の誤読は
  実測した17値では0だった。⚠️ **異体字は名称の突合を壊す**ので、
  名称を配布物に使う判断をするなら正規化が要る

- 歳入の款 map は **2020年度以降に限定**（`fiscal_year_from`）。2018〜2019 は款体系が別
  （20〜21款構成。法人事業税交付金・環境性能割の款新設で以降が繰り下がった）。
  款の意味が 2020〜2023 で同じことは、款ごとの節名称の集合が全22款で 2023 と重なることで裏づけた
- 歳入款8「旧法による自動車取得税交付金」は 2019年廃止の旧法定区分の経過措置（`kind=historical`）
- 項「繰入金」は法定の3項（特別会計・基金・財産区）を1項に畳んだ市の区分（`kind=addition`）
- OCR の抽出物（2020〜2022）は raw に残しているが（`mode=ocr` 列で区別）、
  下流は `mode=text` だけを名称に使う。OCR は誤読が混ざる前提の経路で、
  実測では壊れた名称と巻き戻った款コードが実際に core へ流れ込みかけた。
  ⚠️ **エンジンを替えて精度が上がっても、この扱いは変えていない。**
  取りこぼしが3〜4割ある状態で名称を配ると、「名前が付いた目」と「付かなかった目」の
  差が原典ではなく OCR の当たり外れで決まる。使うかどうかは別に決める判断であって、
  エンジンの差し替えに付随して動かすものではない

### recall を測った（2026-08-30）

`bun run eval:extraction` を作って、**原典にあって抽出できなかった目**を数えた
（`ingestion/budget/observations/132195-extraction-recall.json`。観測は commit しない）。
上の表の「抽出した行」は抽出器が出した行数であって recall ではない
— **原典に無いキーを作った行もそこに入っている**（2022 は 57 行のうち 7 行）。

| 年度 | 経路 | 原典の目 | recall（件数 / 金額） | コードも金額も一致（原典比 件数 / 金額） |
|---|---|---|---|---|
| 2020 | ocr | 81 | 51 (63.0%) / 65.7% | 48 (59.3%) / 63.8% |
| 2021 | ocr | 80 | 62 (77.5%) / 94.5% | 60 (75.0%) / 93.8% |
| 2022 | ocr | 81 | 48 (59.3%) / 74.2% | 44 (54.3%) / 72.1% |
| 2023 | text | 79 | 79 (100%) / 100% | 79 (100%) / 100% |

- 経路をまたぐと **ocr は recall 66.5%（金額 77.5%）、text は 100%**。
  ⚠️ **経路が単一の年度しか足していない** — 落とした目には経路が付かないので、
  経路が混在した年度は分母を帰属できない（現データに混在年度は無い）
- **金額ベースのほうが件数ベースより高い**（2021 は 77.5% に対し 94.5%）。
  落ちているのは小さい目に寄っている。件数だけを見ると過小に、金額だけを見ると過大に読める
- **2022 の欠落は読字ではなく段の巻き戻り。** 原典に無いキーを作った行が 7 件あり、
  「教育費国庫負担金」が款3、「不動産売払収入」が款5 に付いている
  （2023 の text 抽出では順に 15-1-3・17-2-1。款15 国庫支出金・款17 財産収入）。
  同じキーが2度出る重複も2件（`3-1-1` が利子割交付金と民生費国庫負担金、
  `5-1-1` が株式等譲渡所得割交付金と財産貸付収入）。
  ⚠️ **捏造したキーのほうは `revenue_accounts_reconcile` でも見える**（抽出物を左に置く
  left join なので、原典に当たらない行は金額が null で残る）。**見えないのは欠落のほう**で、
  1 目だけ抽出して一致すれば満点に見える。recall を別に測る理由はここにある
  （ただし現状あの検査は 2023 しか見ていないので、2022 の捏造は実際には素通りする）
- 落ちた目の上位は補助金・負担金・市債（2020 の `15-2-1` マイナポイント事業費補助金 92.4 億円など）。
  一覧は観測 JSON の `missedMoku` にある
- ⚠️ **測れたのは 62 団体中 1 団体・4 年度だけ。** 三鷹市（132047）は歳入科目名の
  PDF 抽出をしていない（原典 CSV に名称があるので要らない）ので対象が無い。
  この数字は「抽出器の性能」であって「62 団体で出る値」ではない

**hybrid 判定（text 優先）の境界は現データでは踏んでいない**（2026-08-30 実測）。
`MIN_TEXT_ROWS = 3` に対し、2020〜2022 は全 19 ページとも text で 0 行、
2023 は全 18 ページとも 4〜12 行。**表の行が一部だけテキストとして残っているページは無い。**
⚠️ ただし判定の構造上、12 行の表で 3 行だけテキストが残っていれば text に確定して
残り 9 行が黙って消える。**2023 の最小は 4 行**でしきい値の1つ上なので、余裕は大きくない。
